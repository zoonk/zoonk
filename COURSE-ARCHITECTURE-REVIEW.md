## Final architecture checkpoint, 2026-09-12 13:37 local

The implemented model keeps a stable Course, one current curriculum, explicit Chapter levels/outcomes, and a course-specific plan with ordered chapter IDs and content revision. It uses the existing database structures directly; no separate plan-chapter relation or generic graph engine was introduced. Focused AI selection receives real chapter outcomes, preserves selected order, and validates ordering only among selected prerequisites. Known prerequisite knowledge can justify omitting earlier material. Plan changes preserve historical activity and never award proficiency from a starting-level selection.

## Product decisions

Keep one course identity per reusable subject and teaching language. `Course.format` describes the learning product (`core`, `language`, `personalized`, `question`); it must not encode level, user goal, teaching style, or lesson kind. A learner's current path is a selection through a course, not another course or another course-list entry.

Core should have an explicitly authored Overview collection of 3–6 chapters and a comprehensive progression through Basic, Intermediate, and Advanced. The overview is an alternative short entry, not the only beginner foundation and not an arbitrary prefix of a traditional syllabus. The comprehensive progression has no chapter or lesson cap. Language uses six explicitly authored CEFR levels with learner-readable can-do descriptions, never generic core levels and never ordinal chapter slicing. Question defaults to a single chapter; this reconciles the source's 1–3 chapter allowance with its more specific definition-of-done request for a single-chapter micro-experience. A private curriculum has whatever structure the request needs; do not force it through the reusable intro or overview pipeline.

Allow self-selected starting knowledge immediately, with optional placement assistance later in the same entry flow when useful. Selecting B1 is a starting preference, not a certification or completed A1/A2 credit. For an uncertain learner, a plain-language can-do description and a changeable selection is more reliable than inventing a diagnostic without evidence of its validity.

Separate generic topic routing from private discovery. A normal goal such as learning Python for work can select reusable chapters. An unusual brief can lead to private generation after dynamic follow-up questions. User answers, interests, employer details, and private prompts must never reach shared course generation, public identity search, shared prompt cache, or public metadata.

## Minimal domain model

Use the existing `Course` as the stable identity and ownership boundary. Add an explicit curriculum schema/version field that distinguishes pre-redesign content from the current contract. Course descriptions and public titles remain generic for reusable formats. Published describes content readiness; access separately distinguishes public content from owner content.

Add authored chapter level and concise outcome metadata. Core and language level validation is format-aware. Private and question courses may have no level. Preserve chapter thumbnails for every generated chapter. Do not assign CEFR or difficulty by chapter percentage during migration.

Keep the existing unique `CourseUser(courseId, userId)` enrollment and add one `CourseLearningPlan` per user/course for active preferences: goal, starting knowledge/level, intended scope, optional study-time preference, and activity preferences. Keeping the plan separate from enrollment allows existing enrollment and progress to survive an unconfigured or replaced plan. Stable operational fields remain typed columns; reserve validated JSON for private discovery answers and briefs. Global interests and accessibility-related preferences remain on `UserLearningProfile`.

Use one active path per enrollment, with ordered selected chapter references and the curriculum version it was planned against. A small relation with enrollment, chapter, and position provides integrity for custom selection. Default Overview/full/CEFR selections can be derived from authored levels; persist custom ordering only when there is a actual goal-specific plan. Do not introduce a generic graph engine, multiple named paths, or learner-visible controls for every internal dimension.

Have a single Core path capability return the selected chapter order, required lesson order, progress, next target, and completion state from the same policy. Course CTA, Home Continue, chapter continuation, lesson completion CTA, API, and existing Apple equivalents must consume that rule. Path completion is separate from durable account achievement: changing from overview to the full course opens a new path while preserving all completed learning.

For private discovery, create an owner-scoped request resource with prompt, answers, an incrementing revision, next question or ready outcome, generated brief, and eventual course ID. Follow-up generation evaluates the full existing conversation and asks the next material question. There is no product question-count cap; each step is resumable, rejects stale submissions, and has rate/budget protection. Avoid repeatedly asking information already supplied. A repeated start uses the same request ID and generation claim.

Tracks are learner-owned ordered collections of existing course identities. Use `Track` and a unique `TrackCourse(trackId, courseId)` relation; do not fork member courses or infer shared content from combining their titles. Detect coequal topic requests before single-course canonicalization. Track creation/resume and course resolution are one authenticated Core capability. Progress is derived from each member's active path, with completed/total course counts and a clear next course. Do not duplicate a course once per track in the ordinary library feed.

Every workflow context should capture `{ courseId, contentRevision }` before AI work. Before each persistence transaction, lock the stable Course row, check that revision and the workflow run claim still match, then write; a preflight SELECT without a transaction/lock is insufficient. Replacement takes the same lock, increments contentRevision, swaps current children, updates contract version and plan revision, and invalidates relevant tags. An old result is deliberately discarded or marked superseded; it must not overwrite the new cover, metadata, outline, or activity rows. This makes future version changes a repeat of the same explicit mechanism.

## Access and generation economics

Generated public content is consumable by guests, free users, and subscribers at every level. Authentication is required for all new content generation and durable personal progress. Private content is owner-only, regardless of subscription. Free users receive the same generation capabilities with a smaller budget; a selected B1 or Advanced chapter is as eligible as chapter zero.

Keep the existing atomic first-producer claim mechanism. Reusing completed content and joining an active workflow does not consume another allowance. A paid plan does not bypass ownership or input validation. New quota state should describe a limit and reset/upgrade outcome consistently to Web and API.

A chapter-based allowance preserves the familiar meaningful sample without making the first chapter special, but a chapter allowance must actually include its short lessons. An independent small lesson cap can otherwise stop a learner halfway through the chapter that was promised. Recommended implementation: reserve a chapter-generation allowance for the learner and make lesson generation within that funded chapter use the grant; enforce separate operational rate controls against automated fan-out. This is an allowance to create missing content, not a paywall around content already generated by someone else. Exact initial free limits should be a centralized reversible product constant and tested at the boundary.

Account for nested generation. Course setup should generate the outline and the learner's selected first chapter/lesson, not always position zero or all optional activities. Do not warm quiz/practice unless requested. Chapter images are required for all generated chapters; their cost must be included in the course-generation budget. Private course generation uses the cheap model policy across outline, explanation, tutorial, quiz/practice, follow-ups, and fallback routing. Private per-step imagery is semantic/necessary only; avoid public landing-page and expensive asset work that provides no private learner value.

The existing quota target is globally unique because shared content has a single first producer. Preserve that deliberate behavior. Private resources have unique owner-bound IDs, so they naturally receive their own claim. A retry after a failed workflow should not permit unlimited fresh AI work merely because the target is already claimed; combine idempotent saved steps with bounded retry/rate policy.

## Optional practice and honest progress

For core, question, and private content, the primary list contains one row per taught lesson. Quiz and practical application are secondary actions attached to the source lesson or its completion screen. Persist explicit source-lesson association for optional activities; do not identify companions only by neighboring positions or translated titles. Keep optional activity rows out of required path counts, chapter/course completion denominators, automatic Next, and preload generation. Completing an optional activity can still earn truthful activity/BP metrics.

Language has a different learning mechanism: vocabulary, grammar, reading, and listening are learning experiences, not a blanket set of optional quizzes. Keep useful supported modes, explain them progressively in optional course preferences, and derive the path from the learner's chosen modes. Never silently convert all language practice to passive explanation. Hiding every required kind must have a clear validation/default rule so the path cannot report false 100% completion.

Pending chapters count as unfinished even before they have lesson shells. Prefer an honest chapter/lesson count over a percentage whose denominator expands invisibly as content generates. A chapter is finished when its selected required lessons are complete; a path is finished when its selected chapters are finished. A learner who skips prior knowledge must not gain completed lessons, score, or BP for skipping.

## Migration and future restructuring

The source permits replacing existing content and only requires durable history to survive. Do not import stricter old-attempt assumptions that every historical chapter/lesson/step ID and URL must live forever. Keep course identity stable for library membership and public links; simplify current content rather than maintaining duplicate legacy curricula indefinitely.

First, make historical records independent of the content lifecycle: change LessonProgress.lesson, StepAttempt.step, and chapter/course achievement content references to nullable `SetNull` where their history is retained. Persist useful historical title/course/lesson identity snapshots before detachment. Current progression joins only live content; lifetime activity and score queries continue to include detached historical rows. Ensure nullable unique-key semantics cannot create duplicate completions for live content, and explicitly distinguish historical badges from the current path state.

Add stable lesson concept keys for future exact carry-forward where the learning objective truly stays the same. An exact retained key can preserve completion; an unrelated lesson must get a new identity. For this one-time redesign, historical metrics are guaranteed while conservative starting-level selection can replace uncertain semantic mapping. AI may propose a mapping, but a model's similarity judgment must not automatically award mastery or duplicate durable lesson-count events. The simplest correct choice is to keep unmatched history detached and let the learner choose the appropriate starting point.

Use a generated Prisma migration to mark existing courses as legacy and backfill historical snapshots; local setup and production deployment use the same migration. Regenerate an individual legacy curriculum only after an explicit authenticated start/continue action, with an atomic generation claim. Generate and validate the replacement outline before replacing the current tree. Keep the old published tree available until the replacement outline is ready. Swap it transactionally under a course/revision guard, detach old progress, retain the course ID/slug/enrollment/preferences, and replan affected active paths. Only then lazily generate the learner's target content. Failure must leave the old tree usable; concurrent requests must observe one winner. Guests never initiate migration generation.

Guard all workflow persistence against a stale course revision/run: an old lesson/image workflow completing after replacement must not republish orphaned or superseded content. A new version should not indefinitely retain a complete second content tree. A simple version marker plus transactional replacement is sufficient unless implementation reveals a concrete need for retained version resources.

`db:sync-content` must preserve every new enrollment preference, path, track membership, historical snapshot, answer count, and nullable content reference. Its old slug/position restore strategy is unsuitable for semantic curriculum replacement. Round-trip tests need live and detached history, nonzero/zero/null values, remapped IDs, and a changed curriculum. Tests must exercise the real restore path, not only snapshot helpers.

## Core and API boundaries

Public Core capabilities derive the caller from `getSession()` and own authorization, persistence, orchestration, and invalidation. Apps supply validated resource IDs and input, never a chosen acting user ID. Reusable public catalog reads may remain shared-cached; request-dependent private reads must use private caching. Do not cache an unauthorized/private result under a public course ID key.

Add runtime schemas and public API operations for current-user learning profile, course plan/preferences, owner-scoped discovery requests, and tracks. Existing course/chapter/lesson/content/progress/next-lesson endpoints must support the new access and path semantics consistently. Register routes in `apps/api/src/lib/openapi/document.ts`; use existing error/result conventions. New generation operations return a durable resource/status and reuse existing event/status transport. Keep the public routing contract additive where possible and update the existing Apple DTOs and calls as part of the same implementation.

Privacy verification must cover catalog/search, metadata/SEO/sitemap, course IDs/slugs, chapter IDs, lessons/steps/content, progress, completion/start, next/preload, review banks, question/context/answer routes, generation status and events, course prompt resolution, edition requests, and cached responses. A non-owner should receive the same absent-resource shape as a nonexistent private resource. Do not expose private user text in public course includes (`getCourseById` currently includes an originating prompt).
