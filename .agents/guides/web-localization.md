# Web localization

How web code reads and writes translated copy with next-intl. What gets translated, and when, is in [translations](translations.md).

- Use `getExtracted` on the server and `useExtracted` on the client. Call the returned `t` with string literals; do not use translation keys or pass translation functions through props or helpers.
- next-intl's server functions can go in `Promise.all`, `getExtracted` only as `const [t, …] = await Promise.all([getExtracted(), …])` with an inline array and no spread: the message extractor reads only that shape, so `Promise.allSettled`, a spread, `.then` or a stored promise leave `getExtracted` undefined at runtime or the message unextracted ([amannn/next-intl#2382](https://github.com/amannn/next-intl/pull/2382)).
- A message's id hashes only its English text, so two identical messages share one translation even with different `description`s. When the same English needs two translations (a person's name and a certificate's name), give each its own `id`: `t({ id: "certificateRecipientName", message: "Name" })`.
- Translate copy in the component that owns it. Do not hoist cheap translation lookups or pass labels solely to avoid repeated calls. Caller-provided copy may be an intentional reusable API.
- Use one ICU plural message, such as `{count, plural, one {# item} other {# items}}`, instead of singular/plural branches. A count that can be zero also gets `=0` (`{count, plural, =0 {# items} one {# item} other {# items}}`): Portuguese and French put 0 in `one`, and Portuguese says "0 aulas". Follow the [shared](../../packages/i18n/.eloqnt/styleguide.md) and [English](../../packages/i18n/.eloqnt/styleguide.en.md) style guides for user-facing text, including their voice, the learner's words (which terms a learner knows, and where each is taught), honest-progress and feature-name rules. How much an app screen says, and what its buttons read, follow zoonk-design's [Words](../skills/zoonk-design/SKILL.md#words); a public page follows its [Marketing pages](../skills/zoonk-design/SKILL.md#marketing-pages).
- When source copy changes, extract through the affected app's dev server or build, translate with `pnpm --filter <app> i18n` (`eloqnt translate`) once the copy is final, and run its `i18n:lint`, following the [translation rules](translations.md). Never hand-edit PO structure, IDs, references, or headers. Unrelated tasks do not need extraction or translation runs.
- In `apps/main`, client components receive only their route's messages (`ClientMessagesProvider` in `apps/main/src/i18n/client-messages-provider.tsx`): every page gets main's catalog and learn's site namespaces (`learnSiteMessages`: what public pages render too, such as feedback, the belts, the goal switcher and the buddy names), the `(app)` frame and the task screens' layouts add every other catalog, the player's included (`scope="learn"`). Wrap a route's `layout.tsx` in `ClientMessagesProvider`, never a page inside the frame, which already has every catalog. `learn` is a static script per locale (`learn-messages/`), so no response carries it; `site` rides in the page's data, so a page's own provider would send it again with every prefetch of that page.
