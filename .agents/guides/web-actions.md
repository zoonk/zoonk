# Buttons, forms and Server Actions on the web

How a control behaves while its request runs, before the page hydrates, when the action fails, and across a resize.

- A button whose action is running takes `busy` on the shared `Button` (`@zoonk/ui/components/button`), never a spinner or a busy label of its own: from the press it ignores presses and keeps focus and its look, with no gray or dimming, and a spinner takes the place of its `icon` (pass a button's icon as `icon`, not as a child), so its size and label never change. A button shows one glyph at most ([craft I6](../skills/zoonk-design/references/craft.md#i6-one-glyph-on-a-button)): an icon leads the label, the forward chevron (`FORWARD_ICON`: next, continue, see the result) trails it, and a main action that Enter presses shows only ⏎, last, where its spinner goes. A button whose label changes with its state takes an icon for each label, so it keeps one shape. Without an `icon` the spinner covers its content instead, which keeps its place and its accessible name; keep that for buttons where no icon fits or there's no room for one. That includes a button only disabled while its own request runs; a button waiting on another control's request stays disabled only, with the disabled look. A `PendingLink` takes `icon` too, and a button-styled `LearnLink` that may wait, such as onboarding's Start, draws its content with `BusyContent`: main's `LearningLink` is a `group/busy` that's busy while it asks for a lesson to be written and marks itself `data-busy` from the tap (and `data-link-pending` after 400 ms, for a tab's look).
- A control drawn before the page hydrates takes presses then. `HELD_PRESS_SCRIPT` (`@zoonk/ui/lib/held-press-script`) in the page's `<head>`, with `HeldPressCommit` in its root layout, holds each one: the control shows at once that it's on its way (`data-held`, and `aria-busy` when it has none), a second press is swallowed, and the press reaches the control once React owns it, so an `onClick` counts. A form whose action is a client function sends the values it had at the press; an `onSubmit` form has its button pressed again once it hydrates. So a press handler goes on a `button` or a control role (`switch`, `checkbox`, `radio`, `tab`, `menuitem`, `option`), never a bare element; a pressable piece draws `data-held` as it draws its own busy or picked state, as `Button`, `Switch`, the radios and checkboxes and `ListRowButton` do; a form never posts natively; and a control whose press needs the tap itself says so, as a call's start does with `data-held-ask="microphone"` so the tap asks and `openCallAudio` takes what it opened. React resets a form once its action runs, and a `<select>` goes back to its first option, so a form with a select keeps `onSubmit`.
- A text field drawn before the page hydrates takes typing then. React keeps those words on screen but out of the field's state, and puts a textarea back to its server text as it hydrates. `Input` and `Textarea` (`@zoonk/ui`) keep them and hand them to the field's `onChange` as it hydrates, through `KEEP_TYPING_SCRIPT` (`@zoonk/ui/lib/kept-typing-script`) in the page's `<head>`. Build text fields on those two; a raw `<input>` or `<textarea>` spreads `useKeptTyping` (`@zoonk/ui/hooks/kept-typing`) last.
- A Server Action rejects in the browser when the learner is offline, a deploy cuts the request or the action throws, and React shows a rejection inside a transition or a form action as the route's error page. Catch it where the transition or form awaits it (`safeAsync`, `.catch`) and show the screen's own failure, or a toast when the menu that started it has closed. `zoonk/no-uncaught-transition-await` requires `useActionState`'s action to be a function written in the same file, and checks what it, transitions and form action functions await or return, following functions in the same file; it can't see a Server Action handed straight to a `<form action>`, so wrap that yourself, as admin's `useAdminActionState` does. An action that calls `redirect()` rejects there with the redirect, so pass that on with `unstable_rethrow` (`next/navigation`) before showing the failure. A wrapper also means React holds a send made before hydration and makes it once the page hydrates. Don't hand a form the Server Action itself so it posts natively before then: on a partially prerendered page Next 16.4 answers it with a blank page unless the action redirects ([vercel/next.js#99756](https://github.com/vercel/next.js/issues/99756)).
- A request belongs to the visit to its screen, as on Apple ([requests outlive a layout change](../../apps/apple/AGENTS.md#requests-outlive-a-layout-change)). A resize or a breakpoint change rebuilds what it switches: a part drawn twice (a suggestion's line under one width and its panel from it) or a sheet that becomes a side panel. What that change must keep (a typed answer, an open editor, a request in flight and how it went) lives in React state the screen holds above the switch, so every copy shows the same busy state and result. Leaving the screen ends it, success or failure: the screen remounts for each thing it's about (a goal), and nothing of it lives in a store that outlives the screen.
