# Zoonk's design system on Android

Main's design system (`apps/playground/src/design-system/`, values in `packages/ui/src/styles/globals.css`) says what each thing means. On Android each meaning takes the closest Material role, type style or component, so the platform handles font scale, dark theme, contrast and new windows. The theme lives in `apps/android/core/designsystem/src/main/kotlin/com/zoonk/android/ui/theme/`, the shared pieces in `ui/components/` and `ui/format/` beside it. Composables read roles, never values.

## Ground rules

- **Zoonk's scheme, never dynamic color.** `ZoonkTheme` holds four schemes generated from `globals.css`: light, dark, and each with more contrast. A device contrast level of 0.5 or more (medium or high, API 34+) picks the more-contrast scheme, followed live.
- **Primary is ink.** Filled buttons, text buttons, checked controls and the selected navigation item are black in light and white in dark, as on main.
- **Color means something or stays neutral.** Before you color something, find its role below. If none fits, use `onSurface` or `onSurfaceVariant`.
- **Never color alone.** A word, a symbol or a shape says the same thing.
- **Soft in the standard schemes, strict with more contrast.** Lines (`outline`, `outlineVariant`) and colored words are soft by design; the more-contrast schemes make them strong. Don't darken a role to fix one screen.

When `globals.css` changes, regenerate both apps with `pnpm palette` from the repository root (the generators share `scripts/theme/`, whose tests fail when a committed output is stale).

## Type

Geist and Geist Mono, bundled in `:core:resources` (`res/font/`) and set in `ui/theme/Type.kt`, which holds main's roles once: Material's slots for what Material's components and most text use, and `MaterialTheme.zoonkType` for main's roles no slot carries. Its numbers are main's, measured at 390px, as are the Apple app's roles (`DesignSystem/Typography.swift`). Sizes are in `sp`, so they follow the font scale; Bold Text (API 31+) adds its weight on its own. Scripts Geist lacks fall back to the system font. Screens use roles, never sizes.

## Shape and spacing

Main's radii (`--radius`), generated into `ZoonkRadius` beside the palette (`sm`, `md`, `lg`, `option`, `xl`, `xxl`). The theme puts them in Material's slots (`ui/theme/ZoonkShapes.kt`): `extraSmall` sm, `small` md (chips), `medium` option (cards, answer options, stat tiles), `large` xl (panels). Dialogs, sheets and pickers keep Material's `extraLarge`: they're system containers; a content piece that needs 18 takes `ZoonkRadius.xxl`. Buttons take `lg` (`md` when small) through the button wrappers. A shape that isn't a slot's takes `RoundedCornerShape(ZoonkRadius.<name>)`, never a number. Nothing is a pill except avatars, dots and rings. Spacing comes from component defaults and content padding; group with spacing and `HorizontalDivider` before adding a container.

## Foldables

[Book foldables](../../zoonk-design/references/foldables.md) holds the product rule and what goes on each side for each kind of screen, the same as on the open iPhone Duo. On Android:

- **Navigation:** Material's default suite: a bar when folded or in tabletop, a rail when unfolded (medium and expanded windows), and the drawer only on large windows (1200dp and wider, with a medium height), where two panes still fit beside it.
- **Pages:** `PageWithSupportingPane` lays out a page and its aside; the shell's Navigation 3 list and detail (`ListDetailSceneStrategy`, settings, shown only where a list leads) and Statistics' `ListDetailPaneScaffold` take the same `pageDirective`. It gives two panes where each keeps at least 240dp, measured as Material sizes them: where Material splits the window (expanded and wider), and where a vertical fold crosses the page, flat or half opened, so a Galaxy Z Fold's medium window splits too (Material's `calculatePaneScaffoldDirectiveWithTwoPanesOnMediumWidth`). At a fold the panes meet at it through `excludedBounds`, and the fold, not the text, sets each page's width, so a page keeps its aside at any text size, the way a phone keeps its one column. Off a fold the 240dp grows with the font scale past 1, so large text keeps one column there. A lone pane (no supporting pane, a task without an aside) is measured with its text, as a spread is (`spreadFold`): where a fold crosses a page too narrow for it, its one pane keeps to the page before the fold. `pageDirective` excludes the fold and the window after it, since Material lays a lone pane in the first room left counted from the left, even right to left. It does so only where that page holds a phone's column (240dp): a narrower one, such as a page a drawer leaves, keeps its width rather than a squeeze beside the fold. Material's list-detail scene leaves a lone pane to Navigation 3's single-pane scene, which lays it across the window, so the shell keeps the settings list or a Statistics page shown on its own to the page before the fold through `BeforeFold`, and faces a settings page opened on its own (Help or Subscription from the account menu, Memory from the buddy's day) with the settings list, only at a fold (`BesideItsListAtFold`): the page stays the detail pane of a `ListDetailPaneScaffold` whether the list shows or not, so what it holds survives folding. Don't put another width gate in front of these; they decide.
- **Only at a fold:** `atFoldOnly = true` splits a page only where a fold crosses it, for pages that keep main's own layout on wider windows (the catalog's course, chapter, lesson and list pages, and the goal box beside its examples).
- **One column:** a screen that stays one column across the fold yet holds a field or a button keeps to the page before it through `BeforeFold`: search's field, sign-in, every `StatusMessage` (load failures, empty states, gates), the lesson's own gates and waits (`LessonColumnBeforeFold`), and Today's and the plan's own states. Each is a screen with one decision, so the page after the fold stays blank rather than holding filler. A lone pane whose text is too large for both pages keeps its one column there (see Pages), lessons, practice runs and onboarding's questions included. A one-column screen with real content to face faces it through `PageWithSupportingPane(atFoldOnly = true)`, only at a fold: a goal box the goal's examples (Today signed out or without a goal, and the plan after a quick explanation), and Buddy without a goal the buddy's day.
- **Spreads:** the lesson player, practice runs and the checkpoint duel are spreads (`SpreadScreen`): they split where a fold crosses them, and down the middle of a window 840dp and wider (Material's expanded) with or without a fold, as the iPad does, while both pages have room for a phone's column at the text's size. `SpreadScreen` decides once for the screen: `spreadFold` gives its pages, and its top bar, docked action bar, snackbars and sheets read the same split (`screenSplit`), so they agree on every frame; dialogs keep to a fold alone and stay centered on a wide window. On a window wider than two columns each page's column leans toward the split, so the pages meet in the middle. Phones, the outer display and narrower windows stay one column, and so do pages too narrow for the text. Other screens that spread at a fold (search's results, the mistakes notebook, onboarding's questions) still split only there (`spreadFold` outside a `SpreadScreen`, which reads the fold on every frame: a reading that starts once a fold shows sees no fold at first). The learner's turn stays the column it is without a fold, padded past the fold, and the screen is a second column before it, so placed words, filled blanks and typed answers survive folding and unfolding; each column is a TalkBack traversal group, read in page order. What goes on each page follows [the shared rule](../../zoonk-design/references/foldables.md): a canvas a question asks about moves under its prompt before the fold, a worked example's steps and a word's meaning after it (the word's or a letter's sound at the end of its row), and a teaching screen ends its page after the fold with `ScreenHelp` where the buddy can be asked. A screen keeps what the learner did on it in `ScreenWork`, a saved-state holder keyed by the screen and its round: each page's own state, and its canvas as one movable piece that goes with it between the one column and a page. Previous and Next keep it; only a checked attempt coming back moves the round on (`LessonPlayerState.rounds`, which the view model saves with the screens' unchecked answers and shown steps for when Android closes the app in the background). A lesson's end, and a quick explanation's, is a result (`LessonEndPages`): where the player spreads, what was done takes the page before the fold and what's next the page after it, above the way on. Its moment plays once: made again after a fold or a rotation, the end shows as it finished, and the one column keeps its own scroll, so folding back finds it where the learner left it. Practice runs and the checkpoint duel spread the same way through `RunFrame`: a set's passage or a drill's rule leads the page before the fold instead of sitting in the task's aside, and a statement's card and its answers share the screen's draft, so both pages show one pick. Onboarding's placement and level-test questions spread the same way through `SetupColumn` and `QuestionPages`, the question taking the page where its other steps show the plan so far.
- **Bars:** `DockedActionBar` puts its actions on the page after a fold that crosses it. `PageScaffold` and `TaskScaffold` keep one top bar either way: a page's title ends at the fold, a task's title sits beside the way out, centered over the page before the fold, and the actions keep their slot at the bar's end, past the fold, so a sheet an action opened stays open as the book folds. Scaled or partly hidden placements (a page shrinking under predictive back) don't count, so a page keeps its panes mid-gesture. Search keeps its bar and docked panel to the page before the fold; its full-screen results spread across both pages where each has room (`spreadGroups`: what the learner can do before the fold and the places to go after it, or a query's own matches before it and the catalog and the ways to ask after it). Sheets come from `ui/components/ModalBottomSheet`, never Material's directly: it puts a sheet on the page after the fold, as the open iPhone Duo moves its sheets, so Ask in a lesson covers the learner's turn and leaves the question in view. Opened there, Ask is the lesson's side panel, so it hides while the device is closed and comes back when it opens; opened in one column, it stays open. Dialogs come from `ui/components/Dialogs.kt` (`AlertDialog`, `DatePickerDialog`, `TimePickerDialog`) and snackbars from `ui/components/SnackbarHost`, never Material's directly: they keep Material's look and behavior, a dialog's window moved onto the page after the fold and kept within it (on a tabletop, onto the flat half, where a picker taller than that half keeps its height with its buttons there), a snackbar over the actions it sits with: on a spread, the page after the fold, and in a task whose aside has a footer, over that footer. Menus come from `ui/components/DropdownMenu`, Material's menu anchored to the `Box` around its button: beside a fold it opens toward the side of the button's page with more room (from a ⋮ at the end of the page before the fold, toward that page's start) and is no wider than that room, so Material's own placement keeps it on the button's page. On a tabletop it is no taller than the room Material opens it into on its button's half, so it never crosses the fold or leaves its button, and it scrolls when its items don't fit, as Material's menus do in a short window. From a button over the fold it drops down to the fold, or where that leaves less than one item's room and there's more above, opens upward, placed there through Material's `offset`; from a button under the fold it gets the larger of the room below, as Material measures it, and the room up to the fold. `DetailPage`'s `asideBar` pins a bar under its aside, such as the mock chooser's start status and Start under the picked mock. A control outside a pane reads `pageFold(width)` (where the fold starts and ends from the layout's start edge, or null) and keeps off the fold the same way.
- **Inside a pane:** a pane is about a phone wide even on a wide window, so what's inside it chooses its layout by the pane's measured width, not the window's size class, as Statistics' page does beside its list.
- **The hinge:** a `FoldingFeature` is `FLAT` or `HALF_OPENED`, `isSeparating` while half opened (always, on a dual screen), and `occlusionType` `FULL` where a hinge hides content. Zoonk keeps content off the fold in every state, so nothing moves when the device folds. The angle isn't in the API; never tie a feature to a posture.
- **Outer display:** a compact window: the bar and one column, as on any phone.
- **Continuity:** folding and unfolding recreate the activity. What the learner made lives in view models, `DraftHandle`s and saveable state, so their place, their text and the scroll position survive. Saveable state comes back only to the same place in the composition, so what changes with the fold keeps a screen's parts where they were: `TaskScaffold` lays out through `PageWithSupportingPane` with or without an aside, the top bar's actions keep their slot, the learner's turn stays the first column, and the screen's text scrolls with one state in the one column and on the page before the fold, so the reading place follows it. A screen whose parts move between places keeps their state above them, as the mistakes notebook keeps each list's open group and scroll, a mock's result which areas and topics are open as they move across the fold and which question to review the learner reads, so folding mid-review opens the sheet at that question or scrolls the page after the fold back to it, and every list the same items with or without its hero, so a saved scroll points at the same item in both layouts, and the lesson keeps which screens have "From the lesson" open, each for its round. A part with state of its own that changes place moves as one piece instead: inside movable content, saved state is keyed by the content, not by where it's drawn, as the lesson's canvas is.

### Testing on a foldable

- **The emulator:** the `Pixel_Fold` AVD is a Pixel 10 Pro Fold: an inner display of 2076×2152 px at 390 dpi (852×883 dp, an expanded window, the fold at 426 dp) and an outer one of 1080×2364 px. Boot and share it by the [emulator rules](../../../../apps/android/AGENTS.md#emulators-and-builds).
- **Poses:** `adb -s <serial> emu posture 3` opens it flat, `2` half opens it (a book in portrait, a tabletop once rotated) and `1` closes it to the outer display; `adb -s <serial> emu sensor set hinge-angle0 <degrees>` sets an angle. Rotate with `adb -s <serial> shell settings put system accelerometer_rotation 0`, then `user_rotation 1` (and `0` back).
- **Staying awake:** folding locks the device unless apps continue on fold (`adb -s <serial> shell settings put system fold_lock_behavior_setting stay_awake_on_fold_key`); a test AVD without a screen lock also needs `adb -s <serial> shell locksettings set-disabled true`, or folding lands on the lock screen.
- **Screenshots:** with two displays, name one: `adb -s <serial> exec-out screencap -p -d <display id> > screen.png`, the ids from `adb -s <serial> shell dumpsys SurfaceFlinger --display-id` (the inner display first, the outer one second).
- **Pages:** open one as an App Link would: `adb -s <serial> shell am start -n com.zoonk.debug/com.zoonk.android.MainActivity -a android.intent.action.VIEW -d https://www.zoonk.com/plan`.
- **A Galaxy Z Fold:** `adb -s <serial> shell wm size 1856x2160` and `wm density 420` give its 707×823 dp medium window, but the emulator then reports no fold, so it shows only the layout without one; `wm size reset` and `wm density reset` undo it. Look at its split in a JVM render at `w707dp-h823dp`.
- **JVM renders:** fold and pane placement is checked by looking, in on-demand renders ([how](../../verify/references/android.md#look-at-it-without-an-emulator)) and on the emulator, not in permanent tests. `androidx.window:window-testing` publishes a fold to a render: `WindowLayoutInfoPublisherRule` as `@get:Rule(order = 0)` before the compose rule, then, after `setContent`, `overrideWindowLayoutInfo(TestWindowLayoutInfo(listOf(FoldingFeature(activity, state = …, orientation = FoldingFeature.Orientation.VERTICAL))))`. Its default orientation is horizontal, a tabletop. `LessonSpreadScreenshots` shows the pattern; render at the Pixel Fold's `w852dp-h883dp` and the Galaxy Z Fold's `w707dp-h823dp`. It doesn't replay a published fold to readers that start later, so a screen opened after the fold sees none: open it, `waitForIdle()`, then publish. The `ldrtl` qualifier leaves the layout left to right, so a right-to-left render provides `LocalLayoutDirection`. Robolectric's default legacy graphics fake font metrics, so text there doesn't wrap: a render runs with `@GraphicsMode(GraphicsMode.Mode.NATIVE)`, as [the Android verification rules](../../../../apps/android/AGENTS.md#verification-by-impact) say.
- **What to check:** the outer display; the inner display flat and half opened as a book; on its side flat and as a tabletop; the Galaxy Z Fold's width; large text; and that folding or unfolding mid-task keeps the learner's place.

## Components

- **Actions:** the design system's buttons in `ui/components/Buttons.kt`, one look per role as on main: the main action `Button` (ink), a secondary one `OutlinedButton` (an `input` line, ink words), a quiet one `TextButton`, and `DestructiveButton` (pink-red words on their tint). `ButtonSize.Large` (44dp) is a screen's action, which `DockedActionBar` and `TaskActionBar` give their buttons; `ButtonSize.Small` (30dp) sits beside text, such as a page title's action. A button that is only an icon is `OutlinedIconButton` (main's `size="icon"`: `lg` corners, never a circle, as tall as a large action beside it), and a page's "⋯" is `OptionsButton` (small beside a page's title, large beside a detail page's main action), its menu in a `Box` with it. Material's own buttons, tonal and elevated ones included, fail the `MaterialButton` lint check.
- **Fields:** `OutlinedTextField` in `ui/components/TextFields.kt`, main's field on Material's own text field pieces (`BasicTextField`, `OutlinedTextFieldDefaults.DecorationBox` and `Container`): `label` (a string) above the field as main's `Label`, read by TalkBack as the field's label, a 1dp `outline` line with `lg` corners, main's height on one line (the touch target stays 48dp), and an ink focus ring, 3dp with more contrast. `isError` draws main's invalid look: the line in `MaterialTheme.zoonk.destructive` with a soft ring outside it, the message in Material's `error`. The overload over a `TextFieldState` takes a composer's `shape` and `contentPadding`. Material's `OutlinedTextField` and `TextField` fail the `MaterialTextField` lint check.
- **Selection:** `RadioButton`, `Checkbox`, `Switch` and `FilterChip` as they are; a selected `FilterChip` shows a check (`leadingIcon`) so the state isn't color alone.
- **`PageTitleRow`, `PageHeader`, `SectionHeader`:** main's `PageHeader` and `PageSectionHeader`: a page's title (`headlineMedium`; `PageHeader` adds its supporting line) or a section's (`zoonkType.sectionTitle`), a TalkBack heading, with what sits at its end (a page's actions or readout; a section's short fact as `detail`, or a legend or button as `trailing`), which moves under the title when both don't fit, so the title never breaks inside a word to make room for it. A page or section heading beside something takes one of them, never a `Row` with the heading's `weight`, which gives the room to what's beside it first. A page leads its content with its title, as main's pages do: on a `PageScaffold`, whose `title` the bar then shows only once that heading scrolls under it.
- **`LabelChip`:** main's quiet chip (22dp, `md` corners, an `input` line, no fill), a few words beside a title (Plus, "1 week"), optionally with a symbol. Not tappable; a chip people tap is `AssistChip` or `FilterChip`.
- **`Meter`, `MeterParts`, `TaskSegments`:** a share on a track in `tertiary` (Energy and Brain Power pass their color); a meter of weighted parts (`Track`, `Place`, `Solid`); and main's `TaskHeaderSegments`, a task's progress with one `TaskSegment` per screen, question or block (optionally weighted), drawn at main's size, which the lesson, practice runs, the duel, pronunciation and the session draw. Hidden from TalkBack unless given a `contentDescription`, since the words beside them say the number; `TaskSegments` given `done` too reads as a progress bar.
- **`StatusMark`, `DoneMark`, `ProgressMark`:** done is one blue check; skipped a quiet fast-forward; the learner's place a blue dot with a halo, never a fill; ahead a faint dot; part done a blue ring filling on the track. Marks are one line of body text tall, so they grow with the font.
- **`ListRow`:** main's list row, as dense as main's and iOS's (11dp above and below the words, at least 48dp for the touch target), drawn without Material's `ListItem`, whose rows are 56dp and up: a mark in `leading` (sized by `markSize()`), the words in `headline` (`titleSmall`) and `supporting` (`bodySmall`), and numbers, a date or the Plus mark in `meta` (Geist Mono), which ends the headline and moves under it when the words would get too little room. A row that opens a page has no chevron; at its end sits only the arrow of a row with `expanded`, which opens what's under it and tells TalkBack whether it's open, or a control in `trailing`, such as a switch or a button (main's `SettingRow`). `verticalAlignment = Alignment.Top` keeps the mark on the title's first line when the lines under it run long (main's `items-start`). `highlighted` marks the learner's place: `muted` with `lg` corners, reaching 10dp past the words. Rows reach the list's edges and inset their own content by `LIST_ITEM_INSET`, so a list under a heading takes `Modifier.bleed(LIST_ITEM_INSET)` to line its words up with the heading; a nested row moves its mark and words in by `indent`. `ListDivider` is the hairline between a list's rows (main's `divided-rows`), on the words' margin.
- **`GoalRing`, `MomentReadouts`:** a day's ring, filled in `tertiary` by the share of its goal studied over a `GoalRingTrack` that says what kind of day it was; and a moment's results as large numbers among small words, then its facts.
- **`KindMark`, `KindDot`:** a kind's symbol or dot in its color, only where kinds sit side by side. A list of one kind shows state instead.
- **`BeltDot`, `BeltLevel`:** the belt in its color with an edge, and the level button's content (dot and number, read as "Yellow belt, level 3"); the button says where it goes with `onClickLabel`.
- **`answerTone`, `AnswerTag`:** an answer piece's line, fill and words for idle, picked, right, wrong and guess, and the word a checked piece shows ("Correct", "Your answer", "Your guess"). The words stay `onSurface`; only the line and fill change.
- **`FeedbackPanel`, `FeedbackVerdict`, `FeedbackNote`:** what a checked answer got, under the question: the verdict in its tone's words, read by TalkBack as it appears, and a quiet line on where the question goes next.
- **`GoalBox`, `GoalExamples`:** main's goal box (`GoalEntry`): "I want to …" and Build my plan in one panel, the label over the words when it would crowd them, and the examples under it as rows. Every place a goal starts uses it (Today, the buddy, the Plan, the catalog, the start screen, the visitor's welcome).
- **`LessonVisual`:** main's chart (bars or lines, up to three series) and timeline, from a value type each caller reads its API model into with `recode()`. TalkBack reads a chart's values in place of the drawing.
- **`StatusMessage`, `LoadFailedMessage`, `EmptyState`:** a screen that couldn't show (centered, the main action first) and a place with nothing yet (start-aligned, no card).
- **Formatting (`ui/format`):** `formatNumber`, `formatAmount` (money and units, compact for axes), `formatPercent`, `formatProgressShare`, `formatDuration`, `formatMinutes`, `formatDate` with main's `DateStyle`s and `formatTimeOfDay` on the device's clock, all with `currentLocale()`. They write what main's `@zoonk/utils` writes.
- **Plus locks:** the same screen locked with the subscribe action, never a different screen.
- **Celebrations:** a full-screen `Dialog`, once, never on load, still when the animator duration scale is 0.

## Icons

Material Symbols as vector drawables (Outlined, weight 400, grade 0, 24): `pnpm --filter android symbol <name>` adds `res/drawable/ic_<name>.xml`, `--filled` its filled twin for a selected navigation item, `--mirrored` flips a directional one in right-to-left layouts. Pick the closest symbol to main's lucide icon and Apple's SF Symbol, and name both in the mapping's comment: `PlaceIcon` for the app's places, `LearnKind` for kinds. Outlined everywhere else; filled only for a selected navigation item and a mark main fills (skipped).
