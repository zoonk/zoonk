# Learner simulator

`packages/core/src/plans/_test-utils/sim/` lives seeded learners through the real planner, placement, sessions and plan changes, with no AI, and runs the owner's planning rules (`_test-utils/rules/`, `RULES.md`, `checkRules`) after every step. Use it to find or reproduce planner behavior that only shows across a learner's life: a change, a missed day, outlines landing, a refresh that moves the plan.

A life (`SimLife`, drawn from a seed by `generateSimLife`) takes placement, studies, misses days, changes the plan in the editor or through the buddy, lets outlines land, answers Today's proposal to move the phase dates (`proposals`: apply or keep their dates), may state their level in onboarding (`ownLevel`, drawn for an exam with listening skills) and sometimes undoes a change or placement's test-outs right away (a step's `undo`). New life fields are drawn after the existing ones, or from a random stream of their own, so a seed keeps meaning the same life.

## Tiers

- **Pure** (`runSimLife`): the real planner functions on a fixture library loaded once from the test database. Fast; composes the planner the way `computePlan`, `computeChange` and `refreshGoalPlan` do around their reads (`sim-planner.ts`, `sim-change.ts`, `sim-refresh.ts`).
- **Database** (`runSimLifeInDb`): the same life through the real capabilities on a library copy of its own. It also passes what the plan and syllabus screens say, and with `{ questions: true }` a question bank (text questions for every skill, plus voiced recordings for a skill the exam practices only with them), the session's answers and `sessions`. With questions, lessons are written too (`sim-db-lessons.ts`: a check screen on each skill a lesson teaches, the graph skills the fixture links it to or a finer skill of its own, as most Library lessons teach; a lesson the app creates at runtime is written when a session first gives it) and played through the lesson player, so their answers reach the learner model and the checks get `finishedLessons`. Without questions, a lesson ends as a learning event only. Neither tier models the free plan's lesson allowance.
- The checks read what the learner showed they know (`learner.knownSkillIds`) as the planner read it when it last built the plan: answers after that run count from the next one, and an undo brings back the set of the plan it restores. The pure tier's plans carry it (`SimPlan.knownSkillIds`); the database tier watches `loadPlannerInputs` (`sim-db-known.ts`).
- A day's first planning run is a `newDay` to the checks, studied when the learner finished or tested out a plan item on the last day Today gave them a session, as `wasLastDayStudied` reads it: a session of reviews outside the plan alone is a missed day. A refresh that is the first planning run since the learner finished something carries `progressed`. Placement asks in the exam's choice format, as `loadPlacementItems` does, so a Câmara learner answers true-or-false statements. With a question bank, the database tier records placement's answers through `recordLearnerAnswer` as diagnostic answers, as `answerPlacementQuestion` does, so a right one starts the skill's memory and comes back in a review. Without one, no answer writes memory (placement's are attempts only), as the pure tier models it: memory moves exam priority (`loadReadiness`) and what Today counts as studied.
- The conformance test in `simulated-learners-db.test.ts` lives the same lives through both tiers and fails when the pure tier's composition drifts from the real code: each step's plan, what the step was and what the checks read it as (a studied day, a run after progress), and whether a proposal to move the phase dates waits after it. When you change `computePlan`, `createGoalPlan` or `settleNewPlan` (the plan onboarding leaves, `sim-create.ts`), `computeChange`, `refreshGoalPlan`, `announceTestedOutItems`, `replanAfterPlacement`, `changeGoalPlan` (its set-back), `decidePlanChange` (applying, declining or undoing), `replaceWaitingProposals` or the session's day, mirror it in the pure tier until that test passes.

## Fixtures

`sim/fixtures/*.json` are shared Library content (ENEM, OAB, Câmara, a UX career, an English goal, a class test, IELTS with listening), exported read-only from the development database by `pnpm --filter @zoonk/db sim:export-fixtures`. They hold no learner data.

## Tests and runs

- `simulated-learners.test.ts` (fast tier, in the normal core run) and `simulated-learners-db.test.ts` fail on any rule a fixture's lives break that `sim-open-findings.ts` doesn't list, and the fast tier also fails when a listed rule stops breaking. Remove the entry with the fix that makes it pass.
- Others aren't simulated: in both tiers everyone's pace is the learner's own. The real read (`loadPaceSamples`) takes every learner's lessons of the month before a plan's day from the whole test database, where other files and lives finish lessons on any day, so the database tier reads only the learner's own (`sim-db-pace.ts`). A database-tier life needs no special start date to run beside other files.
- `simulated-learners-large.test.ts` runs on demand: `SIM_RUNS=40 SIM_FIXTURES=career SIM_CONFIRM=1 SIM_REPORT=/tmp/sim.md pnpm vitest run src/plans/simulated-learners-large.test.ts` from `packages/core`. It shrinks the first life that breaks each rule to a repro and, with `SIM_CONFIRM=1`, lives it again through the database tier. `SIM_TIER=db` lives every learner through the database tier with a question bank. Exam lives take minutes each; run large batches detached.
- A report's repro is a ready-to-paste failing test: `runSimLife(life)` and an expectation on the rule. `runSimLife(life, { trace: true })` returns the plan after each event.
