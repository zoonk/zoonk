# Zoonk design

Build clean, subtle, harmonious interfaces. **Don't make me think:** make the purpose, available actions, and their consequences easy to understand. Reduce the effort of using the interface while preserving the thought that learning requires.

## Understand the task

Start with the person's goal, knowledge, and context. Identify what they need to decide and what the product can handle for them. Choose the structure before the controls; a feature list is not an interface. Which model may design, build and judge a screen is set in the orchestration guide ([pick the model](../../guides/orchestration.md#pick-the-model)).

Look up the design system first: what every token, type role, shape, pattern and special moment means lives in `apps/playground/src/design-system/` and shows live, in every mode, at `/design` in the playground (`pnpm dev`); the values live in `packages/ui/src/styles/globals.css`. Inspect relevant screens in the current main app and reuse their patterns ([App patterns](references/app-patterns.md)) and [their pieces](#find-the-piece-before-you-build-one). Mockups are a starting point, not the target: judge a screen by using it, and rethink it when using it shows friction, even if the result looks nothing like the mockup. Question patterns that make the task harder.

### Draw the screen before you word it

A learner scans a screen before reading it, and a scan takes in shapes (the biggest thing, marks, numbers, bars), never sentences: a screen that states its facts as lines of text has no hierarchy, however few and well aligned they are. So before any string, component or brief, write the screen's [sketch](references/show-first.md#the-sketch): the one thing the eye lands on, what the learner needs now and nothing more, and for each of those facts the first carrier that works: what's already on the screen, a mark, a number or a meter, a label on one of those, and last a sentence. Draw it at phone size (`pnpm design:sketch`), run [the scan](references/show-first.md#the-scan) on the picture and its squint copy, and build what passes. [Show before you say](references/show-first.md) has the method, its rules (V1 to V3) and the tool.

### Find the piece before you build one

One moment is drawn by one piece everywhere, and one role has one piece: the same job looks, reads and behaves the same on every screen of every area. Before you write a component, a class list or a sentence, find what already draws it. Search by what the learner sees, since a copy usually has another name but the same words:

```sh
rg -l -F "I don't know yet" apps packages -g '!*.po' -g '!*.test.*'  # each sentence and label it shows, web and native
rg -l "ChevronLeftIcon" apps packages -g '*.tsx'        # its icon
rg -l -F "max-w-column" apps packages -g '*.tsx'      # its most specific class: a theme token or an arbitrary value
ls packages/ui/src/components packages/learn/src/_components packages/learn/src/shell packages/player/src/components
```

Use the piece that does this. Extend the one that does almost this, in the same change, and check its other callers. Write a second one only for a different product rule, and name that rule in the PR. Before building a missing web primitive, check the shadcn registry; build with Tailwind utilities and semantic tokens, as [compound components](../zoonk-compound-components/SKILL.md).

These roles each have one piece and one way on every app screen. A screen never draws its own, spaces one its own way or words one differently ([rules and checks](references/craft.md#roles)):

- **A page's top.** `PageTop` (`@zoonk/ui/components/page-top`; inside the app's frame the layout draws `PageTopBar` and the page its `PageTitle`): the bar, then the title; a bar that holds nothing gives its row to the title. No page sets its own top padding.
- **The way back.** `BackLink`: a left chevron and the name of the page it goes back to, always both. A task (a full-screen flow) keeps ✕.
- **A page's own actions.** The end of its top bar (`PageTopBar`'s `actions`): words as a `size="bar"` button, a glyph alone as `icon-bar`, the "…" last. Nothing sits beside a pushed page's title. A tab root (Today, Plan, the buddy) has no bar: its own action ends its title row, in the small size.
- **A screen's main action.** `BottomBar` (`@zoonk/ui/components/bottom-bar`), last in the page: pinned at the bottom on a phone and a computer, the action full width on a phone and at the bar's end on a computer. A screen with no main action has no bar.
- **What opens over a page.** `Drawer`: a sheet from the bottom on a phone, a centered dialog on a computer. A question that needs an answer is an `AlertDialog`, something edited beside the page a `SidePanel`. The piece decides by screen size, never the screen.
- **A button.** Its label and at most one glyph. The main action that Enter presses is an `EnterButton`, and ⏎ is its one glyph, where the spinner goes while it works. A button Enter doesn't press may have one icon, or trail a chevron (`FORWARD_ICON`) when it goes forward. Never an arrow.
- **The small line over a title.** `Eyebrow` (`@zoonk/learn/eyebrow`): a chip written as a sentence, never mono, uppercase or plain text, over a task's, a card's, a sheet's or a question's title. A page's own title has no line over it, and something finished says so in its title, never in a chip.
- **Paying.** The action reads "Subscribe", everywhere: never the plan's name or another verb ([the words learners never see](../../../packages/i18n/.eloqnt/styleguide.en.md#plain-words-first)).
- **A paid feature.** Looks like any other: no badge, chip or card says it's paid. `SubscribeGate` shows once, when the learner tries to use it ([Subscribing and limits](references/app-patterns.md#subscribing-and-limits)).
- **The "none" answer.** Skip. A step with Skip has no "None of these" or "Nothing to add" option.

A [marketing page](references/marketing-pages.md) is outside a page's top and a screen's main action: its top is the public header over a first screen with its own room, and its one action sits in the page, shown in `BottomBar` once the page's own has scrolled away.

Lint, the catalog's word list and `pnpm verify:pages` hold part of these, and `pnpm verify:pages --roles` lays a role's instances side by side; [measuring pages](../verify/references/pages.md#what-it-judges) lists each check, what it tests and what it leaves to the reader (when a gate showed, a button's width while it works).

A rule holds on every screen, and it serves how the screen looks. When following one would make a screen look worse (empty reserved room, chrome taller or wider than what it holds, a number that fits a phone and not a computer), ship what serves the rule's goal and list the departure in your handoff, for the user to accept or overrule; for a role or a shared piece, that means changing the piece, never one screen's copy ([when a rule looks wrong](../../guides/exceptions.md)). What the user accepts is listed in [craft](references/craft.md#exceptions-the-user-granted) so nobody "fixes" it later. [Rethinking a screen](#rethink-when-stuck) changes its structure, never a role's way.

## Shape the experience

Resolve unnecessary decisions, give attention a clear order, make each element earn its place, organize complexity around the task, make behavior predictable, build confidence, design the whole journey and express care: [design foundations](references/design-foundations.md) says what each asks of a screen and why.

## Words

A screen tells the learner one thing, and its words are what's left once its [sketch](references/show-first.md#the-sketch) has drawn each fact: mostly labels on something drawn, in words the learner already knows. [Words](references/words.md) has the rules for every string on a product screen (the one free line, terms and names, buttons, what to say when) and the order to fix one a learner doesn't understand.

## Marketing pages

The landing page, the catalog, public course, chapter and lesson pages, pricing, shared links and the blog are read by someone who doesn't use Zoonk yet and is deciding whether to try it, so the Words budget doesn't apply. Write, edit and judge them by [marketing pages](references/marketing-pages.md): the order a page answers a visitor's questions in, its one action, search, the skills to write it with and its first-glance test.

## Zoonk's learning experience

- **One calm experience.** Every learner gets the same interface. Playful mechanics (the buddy, the Trickster, missions, Hyperdrive, belts) live inside it, in the same visual language, and never change what someone learns, earns, or sees as progress.
- **One next step at a time.** Lead with the next action and let everything else wait where people go looking for it. On a wide screen the page's work fills the main area beside the sidebar; supporting status and properties (Today's week and preparation, the Plan's numbers and settings, a subject's progress) sit in the aside, never a second main column.
- **One main action per screen; structure stays visible.** A screen answers one question and has one main action, pinned in the bottom bar. A sheet does one job too: it holds only what that job needs (a sheet that adjusts the plan has no feedback question and no "tell the buddy"). Around it, the structure stays in sight: the page's name as its title, each block of content under its own header, lists as one kind of list. Clean comes from that order, not from removing titles and headers. When a result or summary has several things to say, lead with the numbers that matter on its first screen, put the rest in steps after it, and skip the steps with nothing to say.
- **Visible structure.** Show what someone is learning in their own terms (an exam's subjects and topics, a course's chapters, a language's levels and units), with honest progress, so they can trust the plan covers everything. A long list of items without its structure reads as random.
- **Honest progress.** Show progress as it is, from the person's own work, and never promise a result. Follow the [English style guide](../../../packages/i18n/.eloqnt/styleguide.en.md) for progress wording.
- **Kind motivation.** Rewards come from learning, and what earns one shows where it's earned (a mission's row, a challenge's "7 of 10 to win"). Nothing is random or sold, mistakes cost nothing, and nothing creates guilt or streak anxiety.
- **Finished moments.** Short lessons end with a brief completion moment; the full summary waits for the end of the day's study.
- **Learning is light; tests are tests.** In lessons, practice and review, the verdict comes at the smallest step the learner takes, and after a miss they try again at once. A verdict held until the end and an exam-hard question belong only on a screen that says it's a test.
- **Interaction is learning.** An interactive activity is the learning action: the person moves, predicts, or builds something, and a question checks what they saw. Never add one that only decorates.
- **Readable everywhere.** Neutral text (titles, body, muted lines) meets WCAG AA on every surface it sits on, in light and dark. Colored marks, icons, tints and colored words stay soft in the regular theme and turn strict only under `prefers-contrast: more`; color is never the only cue (a word, an icon, a shape or the mark's place in an order says the same, and a legend is added only when none of them does). Theme, contrast and reduced motion follow the device, and every animation has a calm reduced-motion version.

## Zoonk's visual language

The look is **Instrument**: a calm study instrument in the spirit of Linear and Vercel, a quiet body where color marks only what has a different job. Neutral tone steps set a page's parts apart, soft color goes only to meanings, numbers that matter get a readout and a meter, and every page keeps its structure. Ask of every screen: would Linear ship this? The design system (`/design` in the playground, `apps/playground/src/design-system/`) is the reference; this section is the short version.

- **Type.** Geist (`font-sans`) for words, writing and quotes included (an essay's box, a typed answer, a quoted source; never a serif, except a formula, which keeps its math face); Geist Mono (`font-mono`, tabular) for data in rows and lines: minutes, counts, dates, percentages, a row's trailing value. One role per job: `text-display` (the landing), `text-headline` (a public page's name), `text-title` (an app page's or a task's title), `text-section` (a public page's part), `text-lead`, and `PageSectionTitle` for an app page's block. **Titles, not labels**: a page's parts are named by sentence-case titles; uppercase `text-label` stays inside panels. A block's one big number is a **readout** in the text face with tabular figures (`BigQuantity`, `text-readout`), its unit small and muted. Body is 14px in the app; rows are a 14px title over a 12px muted line.
- **Flat first, fewer boxes.** Content sits on the page. A list is flat rows with a hairline between them (`ListGroup`), as wide as the column; the current or next row is highlighted a little past the column's edges. A panel (`Surface`: `bg-card`, hairline, `rounded-xl`, no shadow) is for one self-contained thing, used sparingly and never inside another panel. A public page separates its parts with neutral bands (the page and `ground`), never inside the app; a course's, chapter's or lesson's page uses Route's line instead (`@zoonk/learn/route-line`), a pale line in the subject's color through the course's real order. Overlays (the palette, menus, sheets) may cast one soft shadow; nothing else does.
- **Color.** Soft and purposeful ([color](references/color.md)), one meaning per hue on every screen: blue (`success`) is progress made, up to where the learner is (done is a fill or a check, the place a ring or a dot with a halo); the text color is the action and the learner's pick before it's judged (ink mark on its tint); pink-red (`destructive`) is wrong or removed; amber (`warning`) is look here, including the lessons a plan change takes out of the plan; violet (`brain`) is Brain Power and nothing else. A kind of thing in a mixed list is its icon in its hue from `KIND_MARKS` (`KindMark`), its shape telling it apart, never hue alone; a list of one kind marks state (`StatusMark`); something done is one blue check (`DoneMark`). A course's subject is its label (`SubjectLabel`) and its line (`bg-subject` under `data-subject`), never a wash. Fills and marks take the plain token, words the `-text` token. Everything else is neutral, and navigation recedes: the sidebar is the page's white (black in dark) behind a hairline, its current item on `muted`. Settled calls: a pick is the text color, never blue (blue would say "right" before checking); a call's stars are progress blue, never gold; a belt wears its full colors, the one identity color that stays strong. A few earned moments may be louder (today's missions complete, Brain Power earned): a solid fill and a short motion, never a new color.
- **Progress as data.** A readout with a meter under it says the number and what it's made of: `MeterParts` (6px in the app, 8px on public pages), each part sized by what it measures and colored by what it is (progress blue, the learner's place as a blue ring, the rest on the track). Segments for steps: the day's blocks as equal parts (`DayMeter`, the same on Today, over the session and at every block's end; parts to do stay on the track whatever their kind, named by the rows and its popover), a plan's phases sized by their days; a task's screens under its bar in thinner segments (`TaskHeaderSegments`: blue right, pink-red wrong, the current one a blue tint); cells (8px, 3px gaps) for units counted toward a goal, done in blue, outlined in blue for what's planned next; rings for the week's daily goals; KPI tiles (`StatTile`: hairline, a colored icon before a quiet label, a readout) for results. A plan change is a mono diff (`DiffLines`, `PlanEffectDiff`), colored by what it means.
- **Shape.** Sizes and radii come from the pieces and their tokens ([control sizes](references/craft.md#control-sizes), [shape](references/craft.md#shape)): a screen's action in the bottom bar is 44px, a field and a row 44px on touch and 36px with a mouse, every container `rounded-xl`, a chip `rounded-sm` so it never reads as a pill. The primary button is inverted, the secondary (`outline`) see-through with the stronger line. Nothing is a pill except avatars, dots and rings, and everything tappable is at least 44px to press (`hit-area` where it looks smaller; Today's day bar and a menu's rows with a mouse are the [exceptions](references/craft.md#exceptions-the-user-granted)).
- **Layout.** Every app page lives in one frame (`(app)/layout.tsx`), onboarding and a mock's chooser included, for visitors too, so navigating swaps only the page, never the sidebar or the bars; only the player's task screens are full screen. From `lg` the page starts 40px from the sidebar, its title, tabs and content on one left edge, and fills the room: a wider screen gives the content more room, never a wider margin. [One frame](references/app-patterns.md#one-frame) has the widths, the aside, a tablet's and a phone's chrome and what centers; [tasks and steps](references/app-patterns.md#tasks-and-steps) has the player's.
- **Book foldables.** Unfolded, an iPhone Duo, Galaxy Z Fold or Pixel Fold reads like an open book, a pane on each side of the fold: [book foldables](references/foldables.md).
- **Celebrations.** The special moments (a task's end, missions, a level, a milestone) are warmer and bolder than everyday screens, louder with a solid fill and a short motion, never a new color, and built one way: [celebrations](references/celebrations.md).
- **Motion.** Everyday screens stay still: nothing animates in on its own, and a short transition (150–200 ms) shows what an action did. Only rare earned moments (a level, today's missions, a belt, a lesson's end) celebrate, once, with a spring, a number counting up or a burst, louder as they're rarer; the buddy and the Trickster react with their parts where something happened (never as one block) and hold still where they only illustrate a screen. [Zoonk motion](../zoonk-motion/SKILL.md) says when and how; `/design/motion` moves every pattern.
- **Clean is not boring.** Every screen has something to look at before anything to read ([V1](references/show-first.md#v1-one-thing-first)): hierarchy comes from one strong shape (the content itself, a readout, a meter, the buddy or the Trickster where they belong), then size, weight, tone and color that means something. Fewer words alone don't make it, and neither does decoration. One suggestion at a time (`Suggestion`); one way to draw each thing.
- Build every page from the [page templates](references/app-patterns.md#page-templates) (tab root, detail, catalog, section, browse, task, conversation) and their shared pieces. Keep the same placement for the same things on every page: navigation, search, the main action, page widths and alignment.

## The taste bar

Hold every screen you design, build or review to one bar: a principal designer like Jony Ive, or one at Linear, Vercel or Apple, would love it, not merely accept it. It is clean, quiet and exact, so the person sees their task and not the interface. Judge it on the running product against every aspect below, every time, clarity first. Each one is written so a screenshot or a measurement can settle it; [craft](references/craft.md) has every rule behind them, with how to check it and how it usually gets broken. Where one falls short, don't decorate it or nudge pixels: find what makes the screen harder than it needs to be, and change the UI, the UX or both until it's simpler and better. Matching the mockup or what's already there doesn't clear the bar.

- **Clarity.** Someone who has never seen Zoonk can say what this screen is and what to do, from the title and the main action alone. On an app screen, count it: lines between the title and the main action that belong to nothing drawn (one at most), words on a screen that asks for a decision (60 at most), terms no earlier screen taught (none), places the same fact appears (one, drawn or written). On a [marketing page](references/marketing-pages.md) the counts don't apply: check that each section answers a question a visitor has, in order, under a headline that carries its point alone. Then subtract: remove a box, a label, a divider or a sentence; if the screen still works, leave it out.
- **Hierarchy.** Squint, or open the squint copy: what you see first is what matters first, it is drawn and not a line of text, and no stack of lines follows it ([the scan](references/show-first.md#the-scan)). There is one strongest thing (the content or a moment's hero, then the main action), and [one filled button](references/craft.md#d4-one-strongest-thing) says which button is filled where a dialog, a sheet or a suggestion shares the screen, with two button styles in a bar at most. The eye moves in the task's order, from what this is to what to do next. Anything competing with the strongest thing goes quieter or goes away; order comes from size, weight, tone and position, not from boxes or decoration.
- **Edges and alignment.** In a column, text and boxes start on its start edge and end on its end edge, within 1px. A list whose rows show a mark has one more edge, where every label starts, mark or no mark: a row without one keeps the mark's room while the others show theirs. A bare glyph at an edge (a back link's chevron, a row's chevron, a "…") lines up by its ink, not by its box (`Button`'s `edge`): no part of it passes the edge, and it sits with the letters of the text on that edge (the chevron starts where the title's first letter starts), since letters start a little inside their box. In a list or the sidebar, marks share one center line and labels one start. Things side by side share a top and a bottom. On one line of a row, every part (a lead, a mark, the label, a value, an end glyph) is level by the middle of its capitals, whatever its face or size; text shares a baseline only with text of its own face and size, or inside one phrase. A column is start-aligned or centered, never both, and whatever reaches past it reaches the same on both sides. ([Rules](references/craft.md#edges-and-alignment))
- **Spacing and density.** Space between blocks is a multiple of 4px; 2px steps (2, 6, 10) belong inside a control. The same kinds of things sit the same distance apart, in a group and on every screen, and the space above a section title is at least 1.5 times the space below it. Rows of one kind are one height and dividers one length. Density fits the job: a list to scan stays compact, a decision gets room, nothing is cramped at 390px, stranded at 2560px or drawn empty. ([Rules](references/craft.md#spacing-and-rhythm), [density](references/craft.md#density-and-balance))
- **Shape and control sizes.** A corner's radius is its role's token, never a literal, and a rounded box inside another takes the outer radius minus the gap between them. Controls on one row share one height from the button sizes, a filled and an outline button of one size look one size, and the same control (back, close, "…") is one size on every page of a kind. ([Shape](references/craft.md#shape), [sizes](references/craft.md#control-sizes))
- **Typography.** One role per job from the type scale, three levels in a block at most (so three sizes at most), no size written on a screen (`text-[…]`), and two headings that differ are at least 1.15 times apart. The right face for every number: a readout in Geist with tabular figures, data in mono, a number inside a sentence in the sentence's face. Reading text runs 45 to 90 characters a line; no uppercase sentences, no orphaned word in a title, en dashes for ranges and an ellipsis character instead of three dots. Balance the lines of short titles, captions and centered text (`text-balance`, Android's `LineBreak.Heading`); left-aligned sentences, such as a question, a description or an error, fill their lines and only avoid a lone last word (on the web every text does unless its role balances it, so add nothing; Android's `LineBreak.Paragraph`), since even lines there leave a ragged gap on the right. ([Rules](references/craft.md#type))
- **Color and contrast.** Count the colors on the screen: each one means something from the [color rules](references/color.md), no two meanings share a hue, and nothing is colored to decorate. Neutral text meets WCAG AA on every surface it sits on, colored marks stay soft until a device asks for more contrast, color is never the only cue, and dark mode looks designed, not inverted.
- **Iconography.** One family at the design system's sizes (`ICON_RULES` in `apps/playground/src/design-system/shape.ts`; SF Symbols and Material Symbols in the native apps), icons side by side one size, the stroke never overridden above 12px, level with its text (centers within 1px), bare beside its words rather than in a tile. An icon is there to carry a fact in place of words, or to make something seen often findable without reading; one that only sits beside a sentence saying the same goes. The same icon means the same thing everywhere, and one thing has one icon: the way back is a left chevron, forward a right one, close is ✕, more is "…". ([Rules](references/craft.md#icons))
- **States and consistency.** The same thing looks and behaves the same everywhere: compare the screen with its siblings in every area (other page tops, other task ends, other lists, other asides), side by side in [the role read](references/craft.md#the-role-read), and reuse their pieces before drawing a new one. Every control has a rest, hover, pressed, focus, disabled and busy look; a pick, the current item and the current tab are each drawn one way; no state changes a size or moves a neighbor. Then the details: numbers in a column line up and end together, nothing truncated that the person needs, no layout shift when data arrives. ([Rules](references/craft.md#states))
- **Behavior.** The same control does the same thing on every screen, by key and by click, because the piece that draws it carries its key: each shortcut shows its keycap (`ShortcutKbd`) and is in the one list `?` opens, number keys answer a screen's one list of choices, a key presses only what is on screen, every panel closes with Esc, a press outside and its ✕ and gives focus back, and Esc does what ✕ does without losing work. ([Rules](references/craft.md#behavior))

Judge every aspect in every state: 390 and 1440, light and dark, more contrast, long Portuguese and German words, empty, loading, error and keyboard focus, each looked at, not assumed. The bar is the same on iOS and Android, which draw this design inside their native components ([iOS and Android](references/native.md)).

### Rethink when stuck

When a screen keeps missing the bar, reviews return to the same screen, or each fix adds another element, stop polishing: the structure is probably wrong. Ask a subagent that didn't build it for three to five alternative concepts that rethink the screen from first principles, aiming for the simplest UX and UI that does the job. Give it the person's goal, what the screen must let them do, the constraints that hold (the design system, the product rules above, the platforms) and screenshots of the current version, but not your reasoning for it. Each concept is a different structure, not a variation of the current layout, described by what the person sees and does, what it removes and what it gives up. Choose or combine the strongest, prototype it with real content, and hold it to the same bar.

## Check the experience

Use what you built in the production build, at every size, as the people it serves would, with a mistake walked through recovery. Then readers who built none of it judge each new or changed screen from its pictures alone: [the first-glance test](references/checks.md#the-first-glance-test) asks whether it's understood, [the craft read](references/checks.md#the-craft-read) whether it's drawn right, and the role read whether each role is drawn one way. [Check the experience](references/checks.md) has the sizes, what each reader gets and asks, and how findings get fixed.

## iOS and Android

Native apps draw this design inside the platform's own components: the content (colors, type roles, radii, rows, marks, meters, shared pieces) comes from main, the chrome (bars, sheets, menus, gestures) stays the platform's. Read [iOS and Android](references/native.md) before building or judging a native screen.
