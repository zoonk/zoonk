# Zoonk design

Build clean, subtle, harmonious interfaces. **Don't make me think:** make the purpose, available actions, and their consequences easy to understand. Reduce the effort of using the interface while preserving the thought that learning requires. The user's explicit requirements take precedence over this skill.

## Understand the task

Start with the person's goal, knowledge, and context. Identify what they need to decide and what the product can handle for them. Choose the structure before the controls; a feature list is not an interface.

Look up the design system first: what every token, type role, shape, pattern and special moment means lives in `apps/playground/src/design-system/` and shows live, in every mode, at `/design` in the playground (`http://playground.zoonk.localhost:1355/design` from the main checkout's `pnpm dev`); the values live in `packages/ui/src/styles/globals.css`. Inspect relevant screens in the current main app and reuse their patterns ([App patterns](references/app-patterns.md)) and [their pieces](#find-the-piece-before-you-build-one). Mockups are a starting point, not the target: judge a screen by using it, and rethink it when using it shows friction, even if the result looks nothing like the mockup. Question patterns that make the task harder. When the structure is uncertain, prototype with representative content before polishing.

### Find the piece before you build one

One moment is drawn by one piece everywhere. Before you write a component, a class list or a sentence, find what already draws it. Search by what the learner sees, since a copy usually has another name but the same words:

```sh
rg -l -F "I don't know yet" apps packages -g '!*.po' -g '!*.test.*'  # each sentence and label it shows, web and native
rg -l "ArrowLeftIcon" apps packages -g '*.tsx'        # its icon
rg -l -F "max-w-column" apps packages -g '*.tsx'      # its most specific class: a theme token or an arbitrary value
ls packages/ui/src/components packages/learn/src/_components packages/learn/src/shell packages/player/src/components
```

Use the piece that does this. Extend the one that does almost this, in the same change, and check its other callers. Write a second one only for a different product rule, and name that rule in the PR. Before building a missing web primitive, check the shadcn registry; build with Tailwind utilities and semantic tokens.

## Shape the experience

- **Resolve unnecessary decisions.** Provide a useful default path. Use known context and reversible defaults; ask people to choose where their preferences or circumstances matter.
- **Give attention a clear order.** Decide what matters now, what supports it, and what can wait. Make the next action obvious; keep alternatives available without giving every option equal emphasis. Reconsider competing elements before fitting them into a tidier layout.
- **Make each element earn its place.** Remove labels that restate the obvious and repeated representations of the same information. Before adding a separate widget, consider whether an existing element can communicate it naturally. Look for simpler combinations of information and action while keeping their meaning clear.
- **Organize complexity around the task.** Sequence decisions when one answer determines what comes next. Keep related information together when people need to compare it. Reveal infrequent detail on demand through discoverable controls. Judge total effort: extra steps and hidden information can create more work.
- **Make behavior predictable.** Use familiar concepts, short labels in words the person already knows, and consistent interactions. Keep needed context visible. If using it needs an explanation, improve the interaction; what guidance is left goes where the uncertainty occurs, when it occurs.
- **Build confidence.** Show state and feedback promptly. Prevent likely mistakes, preserve work, and make correction easy. Keep meaningful choices accessible.
- **Design the whole journey.** Preserve context and consistent placement across transitions. Each addition should fit the surrounding experience. Reusing components alone does not make a coherent interface.
- **Express care.** Make people feel capable and comfortable through thoughtful language, balanced proportions, responsive feedback, and smooth continuity. Delight should remain pleasant through repeated use.

For the reasoning behind these principles, see [Design foundations](references/design-foundations.md).

## Words

These rules are for the product's own screens: the app a learner operates, on the web, iOS and Android, and the tools staff operate. [Marketing pages](#marketing-pages) do a different job and have their own standard.

A learner gives a screen about two seconds and knows only what earlier screens showed them. Write for that person, never for someone who knows how Zoonk works.

- **One message.** Before writing, finish this sentence: "This screen tells the learner ___ so they can ___." The title says it. Everything else supports it or leaves.
- **A budget.** Between the title and the main action: one supporting sentence (20 words at most) and one line of facts (three at most). A list row is a title and at most one short line. A result leads with one number or one sentence. Need more? Make it a step, or put it behind one "Details" link. Never a second paragraph.
- **The learner's words.** Use a product term (plan, focus, phase, time a day, Brain Power…) only on or after the screen that shows the learner what it is. Before that, say the plain thing ("how long you study each day"). The [English style guide](../../../packages/i18n/.eloqnt/styleguide.en.md#plain-words-first) lists each term, where it's taught and the words learners never see. If a string needs a translator note to explain a word, the learner doesn't know the word either: rewrite the string.
- **What they get, not how it works.** Say what the learner gets and what to do. How Zoonk picks, counts, saves, schedules or estimates goes behind a tap (a number's sheet, "How this works"), for the few who ask.
- **Say it when it happens.** A caveat, limit or exception appears where and when it applies (the day a lesson moves, the question a test can't ask), not on the screen where the learner decides to start. Being true doesn't earn a line its place. Being needed now, to decide or to act, does.
- **Buttons are verbs they already know.** "Start", "Continue", "Skip", "Save", "Try again": one to three words. A label never names the next screen, a term from a later screen, a duration or a consequence ("Continue to daily time", "Stop and use my answers"). If the consequence matters, the screen says it once, above the button.
- **Once.** Each fact appears once per screen. A line that would repeat on every row goes to the list's header, or goes.
- **No bookkeeping.** Counts and system states ("Questions on 2 of 18 subjects", "lessons aren't written yet") appear only when they change what the learner does next.

When a review or a walk finds that a learner wouldn't understand something, fix it in this order and stop at the first that works:

1. Remove the thing that needs explaining.
2. Rename it in the learner's words.
3. Show it (a mark, a number, an example) instead of describing it.
4. Move the explanation to the moment it matters.
5. Add a sentence, and take another one out.

Fewer words is not less structure: a page still has its title, its sections and one main action.

Internal tools (Admin, evals, the playground, the CLI) follow the same rules for a different reader: a staff person who knows the domain and shouldn't have to hunt. Each page answers one question, leads with what they came for and makes its actions obvious, in the same word for the same thing on every page (the learner apps' word where there is one). Dense tables are fine. A wall of unrelated sections, a sentence of mechanics under every title, raw JSON as the only view of content and a one-word button that destroys something on the first click are not.

## Marketing pages

The landing page, the catalog, public course, chapter and lesson pages, pricing, shared links and the blog are read by someone who doesn't use Zoonk yet, and by search engines. That person is deciding whether to try it, not operating it, so the Words budget doesn't apply. This does:

- **One decision: "is this for me, and is it worth starting?"** In this order: what this is, in the visitor's words; what they get; why to believe it; what it costs them; how to start. A section that answers none of those goes.
- **Enough, in order.** More text is fine when each section answers a question a visitor really has and the page can be scanned: a headline that carries the point alone, one line under it, then the detail for those who read on. One point per section.
- **One action, repeated.** One primary call to action per page, in the same words each time, visible without scrolling and again after each major section. It may name what the visitor gets ("Start learning free").
- **Specific beats clever.** Outcomes and concrete things (what you'll be able to do, what a day looks like, the real product on screen) over adjectives and over how the system works. Every claim is one we can support, and none promises a result.
- **No insider words.** A stranger knows none of our terms, so the style guide's "never" and "before that, say" columns apply in full. A plan's numbers and states (what fits, phases, lessons not ready yet) are for learners who have a plan.
- **Search matters.** Course, chapter and lesson pages are found through search. Keep what earns the visit (what the course covers, the outline, real lesson text, the questions people ask), with real headings and metadata. Cutting words people search for is a loss; cutting words nobody reads or searches for isn't.
- **Hierarchy still rules.** One thing leads in every view, and a visitor knows where to look: clear, not sparse.

Write and edit this copy with [copywriting](../copywriting/SKILL.md) and [copy-editing](../copy-editing/SKILL.md), check it with [seo-audit](../seo-audit/SKILL.md), and use [marketing-psychology](../marketing-psychology/SKILL.md) for how people decide. Those skills are general: where one suggests urgency, scarcity, fear of loss or a promised result, Zoonk's rules win (no pressure, no guilt, nothing we can't support). A blog post follows [zoonk-blog-post](../zoonk-blog-post/SKILL.md).

## Zoonk's learning experience

- **One calm experience.** Every learner gets the same interface. Playful mechanics (the buddy, the Trickster, missions, Hyperdrive, belts) live inside it, in the same visual language, and never change what someone learns, earns, or sees as progress.
- **One next step at a time.** Lead with the next action and let everything else wait where people go looking for it. On a wide screen the page's work fills the main area beside the sidebar; supporting status and properties (Today's week and preparation, the Plan's numbers and settings, a subject's progress) sit in the aside, never a second main column.
- **One main action per screen; structure stays visible.** A screen answers one question and has one main action, in the same place on every page of its kind. Around it, the structure stays in sight: the page's name as its title, each block of content under its own header, lists as one kind of list. Clean comes from that order, not from removing titles and headers. When a result or summary has several things to say, lead with the numbers that matter on its first screen, put the rest in steps after it, and skip the steps with nothing to say.
- **Visible structure.** Show what someone is learning in their own terms (an exam's subjects and topics, a course's chapters, a language's levels and units), with honest progress, so they can trust the plan covers everything. A long list of items without its structure reads as random.
- **Honest progress.** Show progress as it is, from the person's own work, and never promise a result. Follow the [English style guide](../../../packages/i18n/.eloqnt/styleguide.en.md) for progress wording.
- **Kind motivation.** Rewards come from learning, and what earns one shows where it's earned (a mission's row, a challenge's "7 of 10 to win"). Nothing is random or sold, mistakes cost nothing, and nothing creates guilt or streak anxiety.
- **Finished moments.** Short lessons end with a brief completion moment; the full summary waits for the end of the day's study.
- **Interaction is learning.** An interactive activity is the learning action: the person moves, predicts, or builds something, and a question checks what they saw. Never add one that only decorates.
- **Readable everywhere.** Neutral text (titles, body, muted lines) meets WCAG AA on every surface it sits on, in light and dark. Colored marks, icons, tints and colored words stay soft in the regular theme and turn strict only under `prefers-contrast: more`; color is never the only cue (a word, an icon or a shape says the same). Theme, contrast and reduced motion follow the device, and every animation has a calm reduced-motion version.

## Zoonk's visual language

The look is **Instrument**: a calm study instrument in the spirit of Linear and Vercel, a quiet body where color marks only what has a different job. Neutral tone steps set a page's parts apart, soft color goes only to meanings, numbers that matter get a readout and a meter, and every page keeps its structure. Ask of every screen: would Linear ship this? The design system (`/design` in the playground, `apps/playground/src/design-system/`) is the reference; this section is the short version.

- **Type.** Geist (`font-sans`) for words, writing and quotes included (an essay's box, a typed answer, a quoted source; never a serif, except a formula, which keeps its math face); Geist Mono (`font-mono`, tabular) for data in rows and lines: minutes, counts, dates, percentages, a row's trailing value, the eyebrow over a title. One role per job: `text-display` (the landing), `text-headline` (a public page's name), `text-title` (an app page's or a task's title), `text-section` (a public page's part), `text-lead`, and `PageSectionTitle` for an app page's block. **Titles, not labels**: a page's parts are named by sentence-case titles; uppercase `text-label` stays inside panels. A block's one big number is a **readout** in the text face with tabular figures (`BigQuantity`, `text-readout`), its unit small and muted. Body is 14px in the app; rows are a 14px title over a 12px muted line.
- **Flat first, fewer boxes.** Content sits on the page. A list is flat rows with a hairline between them (`ListGroup`), as wide as the column; the current or next row is highlighted a little past the column's edges. A panel (`Surface`: `bg-card`, hairline, `rounded-xl`, no shadow) is for one self-contained thing, used sparingly and never inside another panel. A public page separates its parts with neutral bands (the page and `ground`), never inside the app; a course's, chapter's or lesson's page uses Route's line instead (`@zoonk/learn/route-line`), a pale line in the subject's color through the course's real order. Overlays (the palette, menus, sheets) may cast one soft shadow; nothing else does.
- **Color.** Soft and purposeful ([color](references/color.md)), one meaning per hue on every screen: blue (`success`) is progress made, up to where the learner is (done is a fill or a check, the place a ring or a dot with a halo); the text color is the action and the learner's pick before it's judged (a 2px ring on its tint); pink-red (`destructive`) is wrong or removed; amber (`warning`) is look here, including the lessons a plan change takes out of the plan; violet (`brain`) is Brain Power and nothing else. A kind of thing in a mixed list is its icon in its hue from `KIND_MARKS` (`KindMark`), its shape telling it apart, never hue alone; a list of one kind marks state (`StatusMark`); something done is one blue check (`DoneMark`). A course's subject is its label (`SubjectLabel`) and its line (`bg-subject` under `data-subject`), never a wash. Fills and marks take the plain token, words the `-text` token. Everything else is neutral, and navigation recedes: the sidebar is the page's white (black in dark) behind a hairline, its current item on `muted`. Settled calls: a pick is the text color, never blue (blue would say "right" before checking); a call's stars are progress blue, never gold; a belt wears its full colors, the one identity color that stays strong. A few earned moments may be louder (today's missions complete, Brain Power earned): a solid fill and a short motion, never a new color.
- **Progress as data.** A readout with a meter under it says the number and what it's made of: `MeterParts` (6px in the app, 8px on public pages, parts 2px apart with 3px corners), each part sized by what it measures and colored by what it is (progress blue, the learner's place as a blue ring, a kind in its hue, the rest on the track). Segments for steps: the day's blocks as equal parts (`DayMeter`, the same on Today and at every block's end in a session), a plan's phases sized by their days; a task's screens under its bar in thinner segments (`TaskHeaderSegments`: 4px, 2px corners, 3px apart, blue right, pink-red wrong, the current one a blue ring); cells (8px, 3px gaps) for units counted toward a goal, done in blue and outlined in blue for what's planned next; rings for the week's daily goals; KPI tiles (`StatTile`: hairline, a colored icon before a quiet label, a readout) for results. A plan change is a mono diff (`DiffLines`, `PlanEffectDiff`), colored by what it means.
- **Shape.** Buttons are 44px for a screen's actions (`size="lg"`, a 15px label), 36px by default (14px), 30px beside text (`size="sm"`, 13px) and 24px inside another control (`size="xs"`, 12px), `rounded-lg` (`rounded-md` at 30px and under), their labels medium at every size; the primary is inverted, the secondary (`outline`) is see-through with the stronger line. Every container (answer options, KPI tiles, panels, cards, menus) is `rounded-xl` (14px), sheets, dialogs and a public page's question sheet `rounded-2xl` (18px), chips 22px `rounded-sm` (6px, so a chip never reads as a pill) with the stronger line. Nothing is a pill except avatars, dots and rings. Everything tappable is at least 44px to press (`hit-area` where it looks smaller).
- **Layout.** Every app page lives in one frame (`(app)/layout.tsx`), onboarding and a mock's chooser included, for visitors too, so navigating swaps only the page, never the sidebar or the bars; only the player is full screen. From `lg`: the sidebar (240px, or 56px of icons once collapsed with its toggle or ⌘B/Ctrl+B, remembered on the device), then the page, 40px from it: its title, tabs and content share that one left edge on every page and fill the room, and a wider screen gives the content more room, never a wider margin: grids gain columns, lists, roadmaps and charts grow, the aside holds supporting context, two plans compare side by side, and prose and forms keep their measure on the same edge; onboarding, which asks one thing at a time like a task, centers its column in the page as the player does, under a bar across the page, and the buddy's conversation centers its column as a chat does ([widths](references/app-patterns.md#one-frame)). From 72rem a page that has supporting context uses `PageWithAside`: the aside runs the screen's full height at its right edge behind a hairline (300px, 320px from 80rem) and scrolls on its own; under 72rem its blocks follow the page. A tablet in portrait is one centered 48rem column with the phone's chrome; a phone has a top bar (goal, level, account, search) and three tabs at the bottom (none under onboarding, until the plan exists). The player's task screens, where the learner does the work (a lesson, a question block, a running mock, a call), are full screen and share one chrome: ✕ and ⋯ in the top corners with the title centered over the column, the progress under it, the content top-aligned in the 40rem column (`max-w-column`), everything the screen shows and what's needed to answer it (a question's situation, picture, chart or table; a drill's rule; an essay's instruction; a reading screen's picture) in that column at every size, what helps with it (the buddy, "From the lesson", a passage several questions share) in an aside on wide screens, a quiet rail at the window's right edge behind one hairline, as wide as the app's aside and drawn without a panel, with the column centered in the room on its left, and one action bar pinned at the bottom with a hairline, its main action in the bottom-right corner on wide screens.
- **Book foldables.** Unfolded, an iPhone Duo, Galaxy Z Fold or Pixel Fold reads like an open book: a pane on each side of the fold, each about a phone wide, flat or half folded, never one stretched column or a tablet layout; [Book foldables](references/foldables.md) says what goes on each side for each kind of screen.
- **Celebrations.** The special moments ([the family](../../../apps/playground/src/design-system/moments.ts), live at `/design/moments`) are warmer and bolder than everyday screens and built one way: a task's result place, then the title, what was earned as readouts (the score in ink, Brain Power in violet; one head for every task's end, `MomentHeader`, and while it saves its title in place over a shimmering line, `PendingMoment`), the day's moment (`DayMoment`, under every result that earns Brain Power or Energy: missions on their violet panel, a level in its belt's colors, Energy amber, each with its 6px meter), what's next, and one pinned action that Enter presses, each part 24px from the next. A graded result (a mock's score) leads with its number, the words naming it small above. A milestone's ceremony is the loudest, full screen before the result it crowned: a centered stage, the buddy large on a disc in the new belt's color, a headline-size title. Louder means a solid fill or a tint whose color is the reward and a short motion, never a new color; each part that moves is its own element with a `data-slot`.
- **Keyboard.** A control answers the same keys on every screen, because the piece that draws it carries them: ⌘B/Ctrl+B collapses whichever sidebar is on screen, Enter presses the main action, Esc does what a task's ✕ does, ↑ and ↓ move through a pick-one list's options, and ⌘K/Ctrl+K opens the command palette everywhere (the search field opens it on phones and tablets). Every shortcut shows its keycap (`ShortcutKbd`) on devices with a mouse or trackpad, in the control or its tooltip; the keys live in one list, shown on the design site's Keyboard page ([behavior](references/craft.md#behavior)).
- **Motion.** Everyday screens stay still: nothing animates in on its own, and a short transition (150–200 ms) shows what an action did. Only rare earned moments (a level, today's missions, a belt, a lesson's end) celebrate, once, with a spring, a number counting up or a burst, louder as they're rarer; the buddy and the Trickster react with their parts where something happened (never as one block) and hold still where they only illustrate a screen. [Zoonk motion](../zoonk-motion/SKILL.md) says when and how; `/design/motion` moves every pattern.
- **Clean is not boring.** Hierarchy comes from size, weight and tone, a readout, the buddy or the Trickster where they belong, and color that means something, not from decoration. One suggestion at a time (`Suggestion`); one way to draw each thing.
- Keep company logos out of app interfaces; use that space for the person's task. Logos belong only on marketing pages and the login page.
- Group through spacing, labels and hairlines before adding a container.
- Write to the [Words](#words) budget.
- Build every page from the [page templates](references/app-patterns.md#page-templates) (tab root, detail, catalog, section, browse, task, conversation) and their shared pieces. Keep the same placement for the same things on every page: navigation, search, the main action, page widths and alignment.

## The taste bar

Hold every screen you design, build or review to one bar: a principal designer like Jony Ive, or one at Linear, Vercel or Apple, would love it, not merely accept it. It is clean, quiet and exact, so the person sees their task and not the interface. Judge it on the running product against every aspect below, every time, clarity first. Each one is written so a screenshot or a measurement can settle it; [craft](references/craft.md) has every rule behind them, with how to check it and how it usually gets broken. Where one falls short, don't decorate it or nudge pixels: find what makes the screen harder than it needs to be, and change the UI, the UX or both until it's simpler and better. Matching the mockup or what's already there doesn't clear the bar.

- **Clarity.** Someone who has never seen Zoonk can say what this screen is and what to do, from the title and the main action alone. On an app screen, count it: text elements between the title and the main action (four at most), words on a screen that asks for a decision (60 at most), terms no earlier screen taught (none), places the same fact appears (one). On a [marketing page](#marketing-pages) the counts don't apply: check that each section answers a question a visitor has, in order, under a headline that carries its point alone. Then subtract: remove a box, a label, a divider or a sentence; if the screen still works, leave it out.
- **Hierarchy.** Squint: what you see first is what matters first, and there is one strongest thing (the main action, or a moment's hero): one filled button in view, two button styles in a bar at most. The eye moves in the task's order, from what this is to what to do next. Anything competing with the strongest thing goes quieter or goes away; order comes from size, weight, tone and position, not from boxes or decoration.
- **Edges and alignment.** In a column, text and boxes start on its start edge, or on the one edge where row text starts after a mark, and end on its end edge, within 1px. A bare icon button at an edge (a bar's back arrow, a row's chevron, a "…") lines up by its glyph's ink, not by its box (`Button`'s `edge`): no part of it passes the edge, and it sits with the letters of the text on that edge (the arrow starts where the title's first letter starts), since letters start a little inside their box. In a list or the sidebar, marks share one center line and labels one start. Things side by side share a top and a bottom, and texts on one row a baseline. A column is start-aligned or centered, never both, and whatever reaches past it reaches the same on both sides. ([Rules](references/craft.md#edges-and-alignment))
- **Spacing and density.** Space between blocks is a multiple of 4px; 2px steps (2, 6, 10) belong inside a control. The same kinds of things sit the same distance apart, in a group and on every screen, and the space above a section title is at least 1.5 times the space below it. Rows of one kind are one height and dividers one length. Density fits the job: a list to scan stays compact, a decision gets room, nothing is cramped at 390px, stranded at 2560px or drawn empty. ([Rules](references/craft.md#spacing-and-rhythm), [density](references/craft.md#density-and-balance))
- **Shape and control sizes.** A corner's radius is its role's token, never a literal, and a rounded box inside another takes the outer radius minus the gap between them. Controls on one row share one height from the button sizes, a filled and an outline button of one size look one size, and the same control (back, close, "…") is one size on every page of a kind. ([Shape](references/craft.md#shape), [sizes](references/craft.md#control-sizes))
- **Typography.** One role per job from the type scale, three levels in a block at most (so three sizes at most), no size written on a screen (`text-[…]`), and two headings that differ are at least 1.15 times apart. The right face for every number: a readout in Geist with tabular figures, data in mono, a number inside a sentence in the sentence's face. Reading text runs 45 to 90 characters a line; no uppercase sentences, no orphaned word in a title, en dashes for ranges and an ellipsis character instead of three dots. Balance the lines of short titles, captions and centered text (`text-balance`, Android's `LineBreak.Heading`); left-aligned sentences, such as a question, a description or an error, fill their lines and only avoid a lone last word (`text-pretty`, `LineBreak.Paragraph`), since even lines there leave a ragged gap on the right. ([Rules](references/craft.md#type))
- **Color and contrast.** Count the colors on the screen: each one means something from the [color rules](references/color.md), no two meanings share a hue, and nothing is colored to decorate. Neutral text meets WCAG AA on every surface it sits on, colored marks stay soft until a device asks for more contrast, color is never the only cue, and dark mode looks designed, not inverted.
- **Iconography.** One family at the design system's sizes (`ICON_RULES` in `apps/playground/src/design-system/shape.ts`; SF Symbols and Material Symbols in the native apps), icons side by side one size, the stroke never overridden above 12px, level with its text (centers within 1px), bare beside its words rather than in a tile. Each icon says something its words or place don't, or speeds up recognizing something seen often; otherwise it goes. The same icon means the same thing everywhere, and one thing has one icon: the way back to a page is a left chevron, close is ✕, more is "…". ([Rules](references/craft.md#icons))
- **States and consistency.** The same thing looks and behaves the same everywhere: compare the screen with its siblings (other task ends, other lists, other asides) and reuse their pieces before drawing a new one. Every control has a rest, hover, pressed, focus, disabled and busy look; a pick, the current item and the current tab are each drawn one way; no state changes a size or moves a neighbor. Then the details: numbers in a column line up and end together, nothing truncated that the person needs, no layout shift when data arrives. ([Rules](references/craft.md#states))
- **Behavior.** The same control does the same thing on every screen, by key and by click: each shortcut shows its keycap, a key presses only what is on screen, every panel closes with Esc, a press outside and its ✕ and gives focus back, and Esc does what ✕ does without losing work. ([Rules](references/craft.md#behavior))

Judge every aspect in every state: 390 and 1440, light and dark, more contrast, long Portuguese and German words, empty, loading, error and keyboard focus, each looked at, not assumed. The bar is the same on iOS and Android, which draw this design inside their native components ([iOS and Android](#ios-and-android)).

### Rethink when stuck

When a screen keeps missing the bar, review rounds circle the same screen, or each fix adds another element, stop polishing: the structure is probably wrong. Ask a subagent that didn't build it for three to five alternative concepts that rethink the screen from first principles, aiming for the simplest UX and UI that does the job. Give it the person's goal, what the screen must let them do, the constraints that hold (the design system, the product rules above, the platforms) and screenshots of the current version, but not your reasoning for it. Each concept is a different structure, not a variation of the current layout, described by what the person sees and does, what it removes and what it gives up. Choose or combine the strongest, prototype it with real content, and hold it to the same bar.

## Check the experience

Walk through the task: can someone recognize what matters, predict what happens next, and recover from mistakes? Check what can be removed or combined without losing clarity. Fix unnecessary interpreting, remembering, and choosing.

Inspect implemented changes in the production build `pnpm start` serves on a phone (390px), a tablet in portrait (820px) and in landscape (1180px), a laptop (1440px), and large desktops (1920px and 2560px), with touch, mouse and keyboard. `pnpm verify:pages` ([verify](../verify/SKILL.md)) screenshots a page on all six in light and dark and flags overflow, shifts and small targets; look at every screenshot. Check affected loading, empty, disabled, and error states, plus focus, touch targets, long translations, dark mode and more contrast (Playwright's `colorScheme` and `contrast`, or the browser's rendering emulation). Use the product as the people it serves would, end to end, with real content: type a real goal, go through onboarding, study day one. Check every page a change can reach, not only the one you redesigned. Recheck observed friction. For proposals, show representative screens and transitions. State what remains unverified.

For substantial features, walk the running product as contrasting learner personas, including their bad days, with [zoonk-persona-walkthrough](../zoonk-persona-walkthrough/SKILL.md). Look for redundant controls, words no earlier screen taught, lines nobody would miss, unnecessary choices, hidden progress, and effort that grows with repeated use.

### The first-glance test

You can't judge your own screen: you know what it means. For every new or changed screen, give an agent that has seen neither the code, the spec nor this conversation one phone-size screenshot and nothing else, and ask:

- What is this screen for?
- What would you tap, and what do you expect to happen?
- Which words or lines don't you understand, or wouldn't miss?

For a [marketing page](#marketing-pages) the reader changes: the agent is someone who has never heard of Zoonk and arrived from a search or a link, it gets the whole page at phone size, and the questions are: what is this, is it for you, what would you do next, and what would make you leave?

A wrong guess, an unknown word or a "not sure" is a finding. Don't explain the screen and ask again: change it, by the fix order in [Words](#words) for an app screen and by the list in [Marketing pages](#marketing-pages) for one of those, or [rethink it](#rethink-when-stuck). Then use the flow yourself, start to finish, as a learner with a real goal.

### The craft read

The first-glance test asks whether a screen is understood; the craft read asks whether it is drawn right, and you can't judge that on your own screen either. For every new or changed screen, once it works and before the designer's review ([verify](../verify/SKILL.md)), give an agent that didn't build it the screenshots at 390 and 1440, the same screenshots of the existing screens that do the same thing (the ones the PR names), and [craft](references/craft.md), and nothing else. It answers [the craft read's questions](references/craft.md#the-craft-read) for each screenshot and reports each fault as [a finding](references/craft.md#a-finding): the place, the rule, what is wrong with its numbers, and whether the fault is the screen's or a shared piece's.

Fix every finding and run the read again on the screens that changed, until it finds nothing it can point at. A fault in a shared piece (a bar, a button, a list row, a token's use) is fixed in that piece, so every screen gets it, never with a margin on the one screen. A finding that the design system itself breaks a rule goes to the user once, as a decision about the system. When a finding is one of the system's [deliberate choices](references/craft.md#deliberate-choices), say so and leave it.

## iOS and Android

Native apps are Zoonk's design inside native components, so a learner who switches phones finds the same app. The content layer is the same on web, iOS and Android, from one source: colors, type roles, radii, list and row anatomy, page structure, marks, meters, characters and moments. `globals.css` generates each app's palette and radii in every mode, each app holds main's type roles once (Geist and Geist Mono), and each builds main's shared pieces once (the page header, section titles, lists and rows, buttons, panels, meters, task segments, readouts, goal rings, chips, answer options and their feedback, fields, the goal box), so screens use roles and pieces, never a hex value, a size or a radius of their own. The chrome layer stays the platform's, tinted with Zoonk's ink and never repainted: navigation containers and bars, tab bars and rails, toolbars, sheets, alerts, menus, pickers, text editing, gestures, Liquid Glass and Material's containers. That keeps what the OS gives for free: resizing, font scaling, Bold Text, more contrast, dark mode, screen readers and new devices. Icons stay each platform's set (SF Symbols, Material Symbols), the closest match to main's. The class names and pixel sizes above are the web's; the [Apple](../apple-human-interface-guidelines/SKILL.md) and [Android](../android-material-guidelines/SKILL.md) skills map each one to its native role and piece.

The [craft](references/craft.md) rules hold in both apps, and the craft read runs on simulator and emulator screenshots the same way, with this split:

- **The platform's.** System bars, tab bars, toolbars, sheets and menus keep their own insets, item sizes, icon sizes and corner shapes. Never nudge a toolbar item to line up with the content under it, and don't report one that doesn't.
- **Ours, in the content.** One start edge and one end edge per column, from the page's shared container (`ZoonkList` on iOS, the page's scaffold and `ListRow` on Android), never from padding on a screen. Marks on one axis and labels on one edge in a list. Space, radii and sizes only from the shared pieces, the type roles and the generated radii, so a screen has no number of its own. Controls on one row share a height, and a filled and an outline button look one size.
- **Targets.** 44pt to press on iOS and 48dp on Android, whatever the control looks like.
- **Icons.** An SF Symbol takes the role and weight of the text beside it; Material Symbols stay Outlined at weight 400. Icons side by side are one size and one weight, and one thing has one symbol across the app.
- **Text sizes.** Dynamic Type and font scale change every size, so check edges and baselines at the default size and at a large one: what was side by side stacks, and still starts on the column's edge.
