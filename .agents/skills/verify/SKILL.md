# Verify

Tests, types and lint prove what they exercise. What proves a change does what was meant is using it the way people will and measuring what can be measured. Run this loop whenever you finish work, before each commit, and before handing off: pick the checks the change needs, run them, fix what fails, run them again, and report the evidence. In Claude Code this skill replaces the built-in `/verify`, which runs before each commit; other agents reach it from the root `AGENTS.md`.

## 1. Size it to the change

Read the whole diff since the work started, then take every row it touches. A one-line copy fix and a new route don't need the same pass; a typecheck alone verifies neither.

| The change touches                                                                                    | Verify with                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Docs, instructions or skills only                                                                     | 2: format, links and frontmatter                                                                                                                                                                                                                                                                                                                                                |
| Logic, data, permissions or an API                                                                    | 2, 3 and 5: run it or call the endpoint                                                                                                                                                                                                                                                                                                                                         |
| Copy, or a small visual tweak on one screen                                                           | 2, and 4 on that page at a phone and a laptop (`--viewports phone,laptop`), its [alignment](references/pages.md#alignment) passing                                                                                                                                                                                                                                              |
| Screens, layout, flows, waits, limits, errors, AI output learners read                                | 2 to 6, with pages measured on `pnpm start` on every screen, their [alignment](references/pages.md#alignment) passing and the screens' [scenarios](references/pages.md#scenarios) reached                                                                                                                                                                                       |
| Data reads, routes, layouts, caching, Suspense, prefetching, client components, bundle or server cost | Also 4 throttled, with `--nav` and a `--baseline`                                                                                                                                                                                                                                                                                                                               |
| Effects, subscriptions, timers, long-lived client state, in-memory caches or workflows                | Also a memory soak (`--soak 10`)                                                                                                                                                                                                                                                                                                                                                |
| Entry points (actions, routes, API), auth, learner data, model calls, uploads or dependencies         | Also the attack in 3 and the security review in 5, with `--intruder` on the pages that show that data                                                                                                                                                                                                                                                                           |
| The Apple or Android app                                                                              | 2, and 3 in the simulator or emulator from the app's `AGENTS.md`; for data loading, stores, navigation or long-lived state, also [measuring the Apple app](references/apple.md) or [measuring the Android app](references/android.md); for a screen's layout, the [Apple](references/apple.md#layout-capture) or [Android](references/android.md#layout-capture) layout capture |
| Opening a PR, marking it ready, or merging                                                            | Everything above for the whole branch (`pnpm verify:diff --base <base branch>`, `pnpm audit --audit-level high`), plus the [sweep](#7-sweep-every-screen-the-branch-touches) when a learner sees the change, the root [PR verification gate](../../../AGENTS.md#pr-verification-gate) and the [picture gate](../zoonk-pull-request/SKILL.md#1-open-it)                          |

## 2. Run the automated checks

Use the [development guide](../../guides/development.md)'s table for the change's checks before a commit: format and lint the touched files (lint after format), typecheck, the affected tests, and the containing suites when the impact is broad. Before a PR, run them for the whole branch on the final tree; CI runs every suite on the PR ([PR verification gate](../../../AGENTS.md#pr-verification-gate)). A check that fails is investigated and fixed, never rerun until green.

Before introducing or modifying a constant, predicate, formula, schema, helper, component or class constant, establish its owner and existing implementations:

- Search the repository with `rg` for the identifier and for equivalent behavior: literal values with their units, kind lists, arithmetic, validation bounds, and the fields a predicate checks; for a piece of UI, its words, icon and classes ([find the piece](../zoonk-design/SKILL.md#find-the-piece-before-you-build-one)). Follow imports and callers beyond the changed files. A new name or an inline expression can hide an existing rule.
- Compare every relevant definition and its consumers, including near copies whose values or branches have drifted. Decide whether they represent one product rule or intentionally different domains; matching numbers alone are not evidence of shared semantics.
- Keep a shared rule in its owning feature module (`@zoonk/core` for reusable business behavior), with direct leaf imports. Respect dependency direction: pass the owner's value into a lower-level dependency when importing the owner would create a cycle. Migrate all relevant consumers (when you extract a piece, every copy moves onto it in the same change) and remove superseded definitions, aliases, types and tests.
- Search again after the change for the old names, values and equivalent expressions. Report the owner, migrated consumers, any remaining copies with their distinct semantics, and the checks that cover the affected consumers. A focused test of the new helper alone does not verify its integrations.

Then `pnpm verify:diff` (`--base <ref>` for a branch) reads the change as a principal engineer, a security researcher and a designer would: every client component, effect, browser fetch, waterfall (an `await` that waits for one it doesn't use), cache, migration, entry point, model call, raw HTML or SQL, public env value, dependency, raw color or `aria-label` it adds, each with the question to answer.

Four nonblocking prompts look for copies in TypeScript source under `apps/*/src` and `packages/*/src`: `Repeated definition`, a module-level `ALL_CAPS` constant or lowercase function the diff adds or edits whose namesakes read alike (framework exports such as `GET` and `generateMetadata` are left out); `Near-duplicate code`, a block of about six lines the diff adds that also appears elsewhere, another added file included, ignoring whitespace, comments and imports; `Restated class constant`, an added class list holding every class of an exported `*_CLASS` constant; and `Same words elsewhere`, an added sentence of five or more words that the web catalogs list for another feature. None of them finds a rule restated in other words or a piece drawn from other classes: the searches above do. A match is a lead, not proof of shared semantics.

For copy, it reads the English catalogs (the web's `messages/en.po`, run the app's `i18n` first; Apple's String Catalogs; Android's `values/strings*.xml`) and lists each string the change adds or rewords that runs past 20 words, is a button label over three words (web only, where its source sits inside a `<…Button>`), hedges ("for now", "so far", "may", "up to"), uses a term the English style guide's "Plain words first" table never shows learners, or comes with a translator note that defines a word. Strings used only on marketing pages (landing, catalog, pricing, shared links, blog) skip the two length checks. They're leads for the designer, never blocking. It also asks about a string that pays in other words than "Subscribe", names the plan outside pricing and the subscription page, or is a "none" option beside Skip ([checks on the source](references/pages.md#checks-on-the-source)); `pnpm verify:catalog` fails on one in the web's catalogs and lists Apple's and Android's.

Answer every item in your report, by fixing the code or saying why it's right; credentials, env files, focused tests and a vulnerable dependency the change adds block.

## 3. Use the change in the running app

Passing checks don't show the change working. Run the app and do what the change is for: click the button, submit the form, finish the lesson, reload to see it saved, come back as the same learner.

- **Web:** `pnpm start` builds this checkout and serves the production build at the URLs it prints, sign-in and mailbox included; verify there, since it's what learners get ([development guide](../../guides/development.md)). While you're still changing UI, iterate on `pnpm dev`, then stop it and check the result on `pnpm start`. Sign in as a seeded persona or your own copy (`pnpm dev:persona`, [development guide](../../guides/development.md#persona-passes)) with the newest code in the dev mailbox. Drive the browser with whatever you have (Playwright, `agent-browser`, a browser extension or the harness's preview) and keep screenshots of the result; `pnpm pr:capture` takes the PR's before and after ([show the change](../zoonk-commit/SKILL.md#show-the-change)).
- **Server errors:** `pnpm start` prints the server's in its output and `verify:pages` reports the browser's. Production shows the browser only a digest or a minified React error, so reproduce one on `pnpm dev` for the full message; with the page open in a browser, the dev server reports what went wrong on both sides: `curl -s -X POST <main URL>/_next/mcp -H 'content-type: application/json' -H 'accept: application/json, text/event-stream' -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_errors","arguments":{}}}' | sed -n 's/^data: //p'`. [next-dev-loop](../next-dev-loop/SKILL.md) lists its other tools (routes, compile issues, logs).
- **API:** call the endpoint as a learner (persona bearer token, development guide) and read the response against the OpenAPI contract.
- **Native:** `pnpm iphone`, `pnpm ipad`, `pnpm android:phone` or `pnpm android:tablet`; tap through the screens. For the Apple app, [measuring the Apple app](references/apple.md) counts requests per screen and tab switch, memory, leaks, idle CPU and hangs on the simulator. For the Android app, [measuring the Android app](references/android.md) renders screens on the JVM at every size and counts requests per screen and tab switch, memory, leaks, idle CPU and jank on the emulator.
- **AI:** nothing calls a model until a learner clicks. Prefer fixtures and seeded personas; when the change depends on what a model writes, walk one real run, keep it small, and say what it cost.
- **Attack it:** for each new or changed entry point (action, route, API endpoint), send what a double tap, a second tab, a retry or someone acting in bad faith sends: the same request twice and several at once (background `curl`s with a persona bearer token, or `Promise.all` of fetches), a field the client shouldn't control (another learner's id, an edited `details`, a reported length or count), an oversized body or file, and the request again after the work failed halfway or after what it made was merged, shared or updated. Then count what was charged, recorded, started and published: each happens once, and a refusal comes before anything is spent. Turn each hole into a regression test at the cheapest layer that reproduces it ([zoonk-testing](../zoonk-testing/SKILL.md)); for a race in core, `holdLearnerLock` and `waitForBlockedStatement` (`packages/core/src/_test-utils/learner-lock.ts`) hold the requests at the learner's lock until all of them wait there. Sequential happy paths never show these.

## 4. Measure the pages

`pnpm verify:pages <path...>` loads each path fresh on a phone, tablets in portrait and landscape, a laptop, a desktop and a wide screen, in light and dark. It fails on errors, layout shift past Core Web Vitals' line, blank frames, slow paints, main-thread blocking, server CPU, sideways scrolling, accessibility and a signed-in learner's data reaching someone else. It lists what to look at (work nobody clicked for, client data fetches, late changes, cut-off text, unprefetched links, slow navigations, memory that keeps growing, regressions against a baseline), reports leads for zoonk-design's craft, role and key rules, and walks each page's states without saving anything. It saves full-page screenshots and every load's paint frames. [Measuring pages](references/pages.md) has the flags, each check's line and what usually fixes it.

- Run it on `pnpm start`. A dev server compiles on demand and shows loading states learners never see, so speed, late changes, prefetching, memory and regressions are judged only on a production build; while you iterate on `pnpm dev`, read only correctness and layout from it. For speed work add `--throttle`, and `--nav` for pages a learner moves between.
- Before you change a page, save a run of it; afterwards pass that run's folder as `--baseline` to see what got slower or heavier, and before and after side by side in the contact sheets.
- For data reads, start the server with `ZOONK_QUERY_LOG=$PWD/tmp/verify/queries.jsonl pnpm start` and pass `--queries tmp/verify/queries.jsonl`: each page's render reports its database time and statements, and flags a statement over 100 ms, a read repeated within the render (one per item, or a fact not shared), results over 1,000 rows and filters no index serves.
- `--email` also opens every path signed out, and `--intruder <another learner>` as someone else: neither may receive the learner's email, account id or full name. `--soak 10` walks the paths ten times and compares memory after the first lap and the last.
- When a page's JavaScript is heavy or slow to start (main-thread blocking, slow interactivity, a bundle that grew), audit what it ships with [next-bundle-optimizer](../next-bundle-optimizer/SKILL.md): oversized client bundles, duplicate dependencies and code that can wait for interaction. The loads table's **Links live** is the measure: until a page's links are hydrated, a tap reloads it.
- For loads and taps, read each tap's response, content and whether it came from its prefetch, and run `--nav` once with `--no-prefetch` and once with `--early`: a tap whose prefetch never landed, and one right after a cold load. They catch a frozen screen that a prefetched walk never shows.
- Narrow the run while you fix (`--viewports phone,laptop`), then run every screen once at the end.
- Timings measure the machine as much as the page when other work is running: past three runnable tasks per core, the report marks speed, memory, slow queries and regressions inconclusive. Main-thread work, request and statement counts and bytes still hold. Compare timings back to back on a quiet machine, or measure on GitHub while this one stays busy ([measuring pages](references/pages.md#on-github)).
- Each load also reports its words, the text elements between the title and the main action, and its longest button label, and leads to a page past zoonk-design's Words budget (and, with `--baseline`, words up by more than 20%). Long-form and marketing pages report counts without leads ([measuring pages](references/pages.md)).
- **Alignment is measured, not looked at.** Each load checks how the declared shared pieces line up (start edges, a mark's axis, the end edge, gaps, even siblings, type tokens, each row's line, the column, a bar's room, what a pinned bar covers, one filled action per surface), writes `alignment.json` and ends with one `PASS` or `FAIL` line; a failure, or a declared part it couldn't measure, fails the run. `pnpm verify:alignment <folder>` judges saved captures, Apple's and Android's layout captures included. [Alignment](references/pages.md#alignment) says how to read a finding and what a shared piece you add or change must declare. States behind taps are named scenarios: `pnpm verify:scenarios` reaches each one at its sizes, languages and text sizes, fails each size where it can't reach one, and compares a state pair's anchors, a placeholder's with its page's ([scenarios](references/pages.md#scenarios)).
- Look at each page's contact sheets first (`screens.png`: every screen in each scheme; `paints.png`: every paint of each load), then open a full screenshot or frame where something looks off. A change to speed or server cost reports the numbers before and after on the same setup.

With `--roles`, the same write-blocked walk saves crops and comparison tables for shared roles across the given pages, including overlays it opens. Missing hooks are reported; differences are leads for the reader ([role sheets](references/pages.md#compare-shared-roles)).

## 5. Review it as a principal engineer, a security researcher and a designer

Each role looks for what the others miss: the engineer for failure paths, data and cost; the security researcher for who else can reach the change and what it spends; the designer for what every screen looks like and how it's used. Their checklists say which of the tools above answers each question:

- [Principal engineer and designer](references/review.md)
- [Security researcher](references/security.md)

You can't unsee how you built the change. For anything beyond a small fix, the reviews run once on the branch before the PR opens, each in a separate agent that didn't write it, all at once, given the diff range, the running app's URL and its checklist ([orchestration guide](../../guides/orchestration.md) for the models). Start only the roles the change needs: the principal engineer for code, the security researcher for the entry-points row in step 1, the designer for the screens row (with zoonk-design's [role read](../zoonk-design/references/craft.md#the-role-read) when the change reaches a shared role). Each tries to break the change and reports only what it can show or trace ([evidence before findings](../zoonk-code-review/SKILL.md#evidence-before-findings)). For code, the principal engineer's review comes from the other model family ([cross-model review](../../../AGENTS.md#cross-model-review)); a review command that runs on the builder's own model family doesn't count as that review, unless it is the only family available. The builder fixes what they find.

## 6. Walk it as learners

For anything a learner can notice, use the product as two to four contrasting personas with [zoonk-persona-walkthrough](../zoonk-persona-walkthrough/SKILL.md), including a bad day, from entry to outcome and back the next day. Use the screen, don't only look at it: is it clear, quick, honest and recoverable, and is anything there that needn't be? Two checks answer that by use, not by opinion: the [first-glance test](../zoonk-design/SKILL.md#the-first-glance-test) on every changed screen, and the designer's "Less" item in the [review](references/review.md). For substantial changes a separate agent walks with only the persona brief and the URL, so it doesn't know how the change works.

## 7. Sweep every screen the branch touches

The steps above read what the builder chose to look at. Faults get through in what nobody looked at: a size, a language or a window nobody pictured, a state nothing reaches, a screen that imports a changed piece and was never reopened, a capture measured but never read, a role or a value drawn one way here and another way there, and a builder's own read that passes what they meant to draw. So before a PR that changes what a learner sees, every screen the branch touches is pictured and read once by eyes that built none of it. Size it to the change: a copy fix sweeps the screens that show the string, and a shared piece sweeps every screen that imports it.

1. **List the screens.** Every screen and state the branch changes, and every screen that imports a shared piece it changed (follow the imports, not the pixels that moved), on each platform the change reaches. A row is a place a person can land: a state, its error, its empty, its limit and its wait included.
2. **Picture them on the production build,** at the sizes, languages and windows where layouts break:

   | Platform | Pictured at                                                                                                                                                                                                              | With                                                                                                                                                                                                                                                                                                                  |
   | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | Web      | 390 and 1440, in English and Portuguese (`/pt/…`, as a `pnpm dev:persona … --locale pt` learner); dark too for tab roots, overlays and an error page. Internal tools also at 390 on their home, a list and a detail page | `pnpm start`, then `pnpm pr:capture after <paths> --email <learner> --viewports phone,laptop --out <folder>` (`--steps` for a state behind taps, `--app` for another app, `--schemes light,dark`), and `pnpm verify:scenarios` for the named states                                                                   |
   | Apple    | iPhone and iPad in portrait; the tab roots also on iPad in landscape and on iPhone at the largest text size                                                                                                              | The [layout capture](references/apple.md#layout-capture) (`node apps/apple/scripts/layout-capture.mts … --side after --out <folder>`) from a Debug build of the committed head                                                                                                                                        |
   | Android  | Phone, medium and expanded windows, and a book posture where the screen has panes                                                                                                                                        | The screens' render tests with the [layout capture](references/android.md#layout-capture) (`./gradlew <module>:testDebugUnitTest --tests '*Screenshots*' --rerun -Pzoonk.shots=<folder>`), adopted with `pnpm pr:media adopt after --to <folder> <render.json>...`; a sheet over its page from `pnpm pr:media device` |

   No model or live call: reach a state with seeded learners, fixtures or a faked run, and list a row nothing can reach without one, with why. Look at each picture before counting its row: a step that lands on the wrong screen still makes a picture. Run `pnpm verify:alignment <folder>` on every folder and fix what fails before the read.

3. **Read them blind.** Rename the pictures to neutral numbers in the order a learner meets them and keep the map back. Readers that built none of it, on a design model ([pick the model](../../guides/orchestration.md#pick-the-model)), get the numbered pictures and zoonk-design's [sweep read](../zoonk-design/references/craft.md#the-sweep-read), and nothing else: not the code, the diff, the spec or what a screen is meant to show. Give one reader a whole flow on every platform it reaches, so the same screen on the web, Apple and Android sits in one set, and run the [role read](../zoonk-design/references/craft.md#the-role-read) across areas for the roles the change reaches.
4. **Check each report** against the rules (craft's [deliberate choices](../zoonk-design/references/craft.md#deliberate-choices) and the [exceptions the user granted](../zoonk-design/references/craft.md#exceptions-the-user-granted)) and, for anything it says it saw, against the picture. Each finding is confirmed, plausible (the picture alone doesn't settle it: check it in the running app), a fault of the capture or the seed, or not a finding, with the rule that says so.
5. **Group by cause before fixing.** A cause is one thing to fix: a shared piece, a formatter, a scenario's seed, one screen's layout. Each finding goes in the cause whose fix removes it, and a fault seen on one platform is checked on the other two in the same fix. For each cause, name why it got through (no scenario reaches it, no check measures it, nobody pictured that size or language, nothing compares it across screens, a piece changed after the read) and [grow the loop](#grow-the-loop) so the next change can't repeat it.
6. **Close a finding only by a fix or a rule.** A finding closes when its fix lands and its pictures are retaken and read again, or when a rule or an exception the user granted allows it. The builder's own read never closes one, and "deliberate" isn't a reason unless the exception list says so. When a shared piece changes after the read, picture and read again every screen that imports it.

The PR still shows only the few pictures that make the change clear, through the [picture gate](../zoonk-commit/SKILL.md#every-picture-is-captured-current-and-read); the sweep is what lets its verification section say the rest was checked.

## 8. Fix and run it again

Fix what fails within the change's scope, rerun the check that caught it, and once everything passes run the change's set once more, since fixes break other things. Never loosen a budget or skip a check to pass: a budget is a product decision, so propose a change to it with the evidence. A finding you leave (a client fetch that has to poll, a shift you can't remove yet) is named in the report with the reason.

## 9. Report the evidence

Say what you ran and what it returned, so nobody has to run it again:

- each check's command and result (counts, failures with their output), and your answer to every `verify:diff` item
- shared-rule searches, ownership and consumer coverage, including intentionally separate definitions and why they stay separate
- what you did in the running app, with screenshot paths, and what each attack sent and caused
- the `verify:pages` report path, its failures and what you changed for them, and the key numbers (before and after for speed work)
- each review's findings and what you did about them, and the persona walk in that skill's format
- for the sweep: the screens it pictured at which sizes and languages, the rows it couldn't reach and why, the readers, and each cause with its findings, its fix and why it got through
- what you couldn't verify and why

"All checks pass" without the evidence isn't verification.

## Grow the loop

When a person (or you) catches the same thing on several screens, first look for the instruction that asked for it: a pattern, a style-guide row or a rule that the screens followed. Fix that, then the screens. Then make the catch something the next agent measures: a rule in `scripts/verify/rules/`, a check in `scripts/verify/checks.mts`, a measurement in `scripts/verify/measure.mts` (each with its unit test), or a line in a reviewer's checklist. An alignment fault goes into the relationship table (`scripts/verify/alignment-table.mts`) when a rule can state it: name the parts, declare the relationship, and add the real capture of the fault and of its fix to `alignment-cases.json` with a test that fails the first and passes the second. When no rule can state it, it becomes a question in craft's [craft read](../zoonk-design/references/craft.md#the-craft-read). Prefer checks with a number and a line over judgment calls; an agent can tell whether a number passed. When a review finds an input that breaks a pure function, the fix adds a property test over that kind of input ([zoonk-testing](../zoonk-testing/SKILL.md)), not only the one example.

Each cause the [sweep](#7-sweep-every-screen-the-branch-touches) groups ends in one of these, by why it got through:

- **No run reached the state** (a failure, a limit, a paused goal, a row left open): it becomes a scenario in `scripts/verify/scenarios/`, with the seed that puts a learner there, so `verify:scenarios` and the read both reach it next time ([scenarios](references/pages.md#scenarios)).
- **No check measured the relationship:** a relationship in the [alignment check](references/pages.md#alignment), declared on its piece or held on [every page](references/pages.md#page-rules), with a failing capture first. A line that ends on a separator, one word alone on a wrapped title, facts line or button, two control heights in one row, content cut or scrolled with no sign of it, and a helper as large as its title are measured this way. A capture records which measurements it took, so a new rule also marks older captures not measured until they're retaken.
- **One value written two ways** (a date, a duration, a range, a count): one formatting module per platform, held by a lint ([checks on the source](references/pages.md#checks-on-the-source)), so a screen can't write its own.
- **Only eyes can judge it:** a role drawn two ways across areas or platforms, a word a newcomer can't know, one thing or one action named two ways, a sentence that reads wrong. The [role read](../zoonk-design/references/craft.md#the-role-read) and the [sweep read](../zoonk-design/references/craft.md#the-sweep-read) ask these, so a question that would have caught it goes there.
