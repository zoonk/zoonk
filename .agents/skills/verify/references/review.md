# Reviewing as a principal engineer and a designer

Each review rebuilds what the change should do from the request, not from the code's own explanation, then checks the diff against it. `pnpm verify:diff` lists the lines to start from, `pnpm verify:pages` measures the pages, and [zoonk-code-review](../../zoonk-code-review/SKILL.md) is the method for classifying and reporting findings.

## Principal engineer

- **Exactly the request.** Every line earns its place (root `AGENTS.md`): nothing speculative, nothing left from an approach that changed, no second way to do what the codebase already does.
- **Failure paths.** Errors, timeouts, retries, a double tap, a second tab, two writes at once, a partial failure. A POST that records, awards or charges does it once (an allowance claimed twice, an award replayed, a newer answer overwritten). Workflow changes run `pnpm --filter api test:workflow`, since the API's regular tests replace the workflow runtime.
- **Data per request.** Each fact is read once per request, lists are bounded, large fields (lesson content, answers) aren't read where they aren't shown, a new filter or sort has an index, transactions are short and hold no network or model calls. When a change adds reads to a page learners open often, extend the read-budget tests (`countDatabaseStatements` and `assertReadBudget`, as in `packages/core/src/view-models/render-reads.query-budget.test.ts`) with small and populated fixtures; reads make no writes.
- **Caching.** A cached function's inputs are everything its result depends on; a write expires exactly what it changed; Next's default lifetimes unless they demonstrably fail. Walk write → read → back and forward → reload, and a write through the API read back in Main, since each helper being right doesn't make them right together.
- **Rendering.** Server first: data arrives with the page, client components hold interaction state, every `"use client"`, effect and browser fetch in `verify:diff` has an answer ([You might not need an effect](https://react.dev/learn/you-might-not-need-an-effect)). Lint already catches an effect's mechanics (state set in an effect, missing dependencies); the review asks what it synchronizes with and who cleans it up. A browser fetch can be right (personalizing a shared public page, following a running workflow); it needs the reason. The React Compiler memoizes, so manual memoization needs a reason too.
- **Cost.** On `pnpm start`, throttled: LCP, blocking time (long tasks that delay taps), server CPU and JS bytes against a baseline run (`--baseline`). A new heavy import gets its route's client graph compared: `pnpm --filter main analyze --output --snapshot before` on the base, `--snapshot after` on the change, then `pnpm --filter main exec next analyze export --snapshot <name> --route <route>`. For long-lived client state, subscriptions, timers, media, workers or in-memory caches, a memory soak (`--soak 10`) shows whether the browser's heap, DOM nodes and listeners or the server's memory keep growing; server memory (RSS) can grow from the allocator alone, so confirm a suspected leak with heap snapshots before and after a lap in DevTools.
- **Architecture.** Rules and authorization in `@zoonk/core`, delivery in the apps, product behavior reachable through the public API, one source of truth for each rule. `pnpm openapi:check` keeps the contract file in sync with the routes; it doesn't show that Main and the API do the same thing, so check that by reading both.
- **Tests.** At the cheapest layer that catches the risk (zoonk-testing), failing without the fix, and none that only mirror the code.
- **Operations.** Errors reach error reporting with context and without learner text; owner steps are in the PR's migration guide. Production applies migrations before it deploys the apps, so the old code runs on the new schema for a while: a migration that drops, renames, retypes, constrains or backfills is deployed to a disposable copy of the previous schema with data first (`pnpm --filter @zoonk/db db:deploy` against it), and nothing deletes learner history by cascade without meaning to.

## Designer

- **Look at everything.** Each page's `screens.png` (six sizes, light and dark) and `paints.png` (what appeared when), held to [zoonk-design](../../zoonk-design/SKILL.md)'s taste bar: one strongest thing, shared edges, type roles, color that means something, siblings that look and behave alike. With `--baseline`, compare the sheets before and after for changes nobody meant to make.
- **States the change reaches.** Empty, error, waiting, long Portuguese and German text, more contrast and reduced motion, checked at a phone and a laptop size. Pick them from what the change touches; `verify:pages` covers sizes and schemes, not states.
- **Keyboard and assistive tech.** Tab through the changed screens: focus is visible on everything you reach, in a sensible order, and never trapped; Escape closes what opened; names say what the screen shows (`verify:pages` runs axe and the 44 px target check).
- **Words and motion.** Copy follows the [style guide](../../../../packages/i18n/.eloqnt/styleguide.md); motion follows [zoonk-motion](../../zoonk-motion/SKILL.md) (everyday screens stay still); nothing flashes, swaps or jumps (the paints sheet and CLS sources).
- **Effort.** Fewer steps, choices and words for the same job; nothing a learner has to remember from one screen to the next. The [persona walkthrough](../../zoonk-persona-walkthrough/SKILL.md) is where that's judged by use.
