# Android app guidance

The [repository guidance](../../AGENTS.md) applies. This file adds Android-specific constraints; setup, commands, and implementation details live in the [README](README.md). Read the sections relevant to the task.

## Scope and architecture

- This Kotlin/Jetpack Compose app targets phones, tablets, foldables, ChromeOS, and resizable Android windows. Main defines product intent, copy, behavior, API contracts and screen structure; Apple shows how a native client reads the public API; the design system defines meaning and look. Build it with Android's default components and behavior, in Zoonk's colors, type and shapes through the theme and the design system's components. Additional platforms such as Wear OS or TV require their own product scope.
- The minimum is API 26: no fallbacks below it, and a version check only where a platform API is newer.
- Keep a single activity. Modules: `:app` (the shell: the activity, the application, `AppEntries`, error reporting), one `:feature:<name>` per product area ([which](README.md#structure)), `:core:resources` (every string, translation, drawable, font and asset; its `R` is `com.zoonk.android.R`), `:core:navigation` (routes, links and the navigator), `:core:data` (the container, `data/`, every store and feature API with the models they return), `:core:designsystem` (the theme, formatters, generic components, and the page and task scaffolds; it depends on no feature), `:core:ui` (learning pieces several features show), `:api` (the generated client) and `:lint-checks` (build time, not in the APK).
- Where code goes: a screen, its view model and its `<Name>Navigation.kt` go in their feature module; a store, its feature API and the models it returns go in `:core:data` with the container; a piece two feature modules show that needs only core modules goes in `:core:ui`; Zoonk's theme and generic components go in `:core:designsystem`; every string and drawable goes in `:core:resources`. Product code is organized by `feature/<feature>/` package, and a shared piece has one owning package that others call. Packages keep their names when files move between modules, so a package can span modules.
- What may depend on what: core modules only on the ones before them (`:core:resources`, `:core:navigation`, `:core:data`, `:core:designsystem`, `:core:ui`); a feature module on core modules and on the feature modules it builds on, never the reverse; `:app` on everything. Gradle fails on a cycle, so a piece both directions need moves down to the lower module or to `:core:ui`.
- Every module applies a convention plugin from `build-logic`, which sets the SDKs, Kotlin, Compose, lint and unit-test options once; a module's own build file keeps only what is specific to it. A new feature module's `feature/<name>/build.gradle.kts` applies `zoonk.android.feature` with namespace `com.zoonk.android.feature.<name>`; include it in `settings.gradle.kts`, depend on it from `:app`, and call its entries from `AppEntries`.
- Test helpers built on a module's types live in that module's `testFixtures`, which other modules' tests use with `testImplementation(testFixtures(project(…)))`. Device tests (`androidTest`) stay in `:app`, which runs them on the whole APK.
- `AppContainer`, created in `ZoonkApplication`, wires everything with constructor injection; don't add a DI framework. What Android creates on its own (services) reads the container through `ContainerApplication`. Debug-only behavior lives in the `debug` source set (with a no-op twin in `release` when main code calls it), never parsed in product code.
- Coroutines: the container's scope for caches and timers, `viewModelScope` for writes, `rememberCoroutineScope()` for UI-only work. Never `GlobalScope`. Retrofit calls are main-safe; use `Dispatchers.Default` only for measured heavy work.
- A snackbar for work that can outlive its screen goes through `AppContainer.snackbars`, never `showSnackbar` on a host captured from the window, which a recreated window drops.
- Scope every asynchronous result and credential change to the session that started it. Before publishing or deleting state, confirm that session is still current, and test meaningful request-order races.
- Usage analytics go to PostHog from release builds only, and only the events main sends from the browser, typed in `AnalyticsEvent` with main's names and properties: composables through `LocalEventTracker` (`TrackShown` for a viewed or shown event), view models through the tracker they're given. Never call the SDK directly, and never send an outcome the server already records from API requests.
- Crashes and errors go to Sentry from release builds only, and a report never names a learner.

## Native UI

- For UI, navigation, or interaction work, use [Zoonk design](../../.agents/skills/zoonk-design/SKILL.md) for the experience and what things mean, the [Android Material guidelines skill](../../.agents/skills/android-material-guidelines/SKILL.md) for components, behavior and icons (Material 3 and Android components styled with the design system's colors, Geist type and shapes), [Zoonk motion](../../.agents/skills/zoonk-motion/SKILL.md) for whether anything moves, and current official documentation relevant to the change.
- Navigation 3 with typed routes: `AppRoute` declares every main path with its presentation and requirement, and `AppLink` reads main's URLs into them. A feature registers its routes' screens only in its own `<Name>Navigation.kt`, and every route opens a real screen: no stand-in ships. Features navigate only through `AppNavigator`, and open web pages only through `openWebPage`.
- Build tab roots on `TabRootScaffold`, pages on `PageScaffold` (leading their content with their title, `PageTitleRow` or `PageHeader`), tasks on `TaskScaffold` and pages with an aside on `PageWithSupportingPane`. Where a screen's top bar shows no title, mark its heading with `Modifier.pageTitle()`, so TalkBack and the keyboard start there when the learner goes to it.
- Adapt to the current window size and available space with window size classes and measured space, never device checks. Preserve state across resizing, folding, rotation, and recreation; keep orientation and resizing unrestricted. Use canonical multi-pane layouts when content benefits from them.
- **Book foldables:** unfolded, a book foldable reads like an open book, a pane on each side of the fold; [the shared rule](../../.agents/skills/zoonk-design/references/foldables.md) says what goes on each side. Lay screens out with the design system's pieces, which already decide where to split: `PageWithSupportingPane` and `pageDirective` (`atFoldOnly` for pages that keep main's layout on wider windows), `SpreadScreen` for lessons and runs, `BeforeFold` for a one-column screen with a field or a button, `TaskScaffold(lonePage = true)` for a task with one decision, and `PageLoading` for a screen's spinner. Read the window's size class and folds with `windowAdaptiveInfo()`, which `ZoonkTheme` reads once for the window, never Material's `currentWindowAdaptiveInfoV2()`, which sees no fold on a new screen's first frames. Take sheets, dialogs, snackbars and menus from the design system (`ModalBottomSheet`, `Dialogs.kt`, `SnackbarHost`, `DropdownMenu`), never Material's directly, and keep any other control outside a pane off the fold through `pageFold`. Don't put another width gate in front of them. Inside a pane, lay out by its measured width, never the window's size class. Never read the hinge's angle or put a feature behind a posture. What the learner made survives a fold, so it keeps its place in the composition or lives above what moves ([details and testing](../../.agents/skills/android-material-guidelines/references/design-system.md#foldables)).
- Preserve edge-to-edge and accessible system bars, consume scaffold padding once, and account for cutouts and the keyboard. Retain Android back behavior, 48dp touch targets, font scaling, TalkBack semantics, RTL, and keyboard/pointer access as relevant controls change.
- Private pictures (the API's `/v1/files/`) load through `images.request(context, url, session)` with the session the screen shows. Never add the bearer through an interceptor that reads the current token.
- Sound goes through the container's `speech` player, one sound at a time for the whole app: listen buttons use `rememberSpokenAudio` and `ListenButton`, and recorded answers `VoiceAnswerRecorder`, or a `VoiceRecorder` in the ViewModel with `rememberRecordTap` and `RecordButton` when the screen's own state grades each take. Never create another `ExoPlayer` or `MediaRecorder`.
- Learner code (JavaScript, Python, SQL, regexes) runs only through the container's `codeSandbox`; never another WebView, JavaScript engine or `java.util.regex` for it. Its page, `assets/sandbox/index.html`, is generated: run `pnpm --filter android sandbox` after main's sandbox changes.

## Data loading and caching

Every read the app shows goes through one pattern in `data/`, so screens are instant on return:

- Stores create their reads with `cache.resource(audience, domains, maxAge, isEmpty) { session -> … }` and own the returned `Resource<T>`; only stores create resources, and stores live in the container for the app's lifetime. A `Resource` already loads once, revalidates in the background, shares one request among callers and follows session changes by its `Audience`, so stores and screens add none of that.
- Each API read has one owning store, and every screen that shows it derives from that store's resource rather than a second read or a copy. A read several screens share gets a counting test (`CountingApi`, the real Live client against a loopback server) so a screen that adds a request fails.
- A screen shows a resource with `val state by store.thing.collectShown()` and switches on `LoadState`; only that collection counts as viewing. Pull to refresh and retry call `refresh()`. Never start requests in `LaunchedEffect(Unit)` or `init {}`, never copy a resource's value into another state holder, and always pass the store's instance.
- Heavy reads by id (course, chapter, lesson, tutor thread, mock result) use `cache.keyed(…)`; never keep resources in an unbounded map. Pagination appends with `resource.update` after checking `resource.revision` didn't change while the page loaded. A task that opens over a screen calls that store's `prepare()` so the screen is ready when uncovered.
- A screen gets a ViewModel, scoped to its navigation entry, only when it writes or holds in-progress work. It exposes store resources as they are.
- Run every write through `cache.mutate(invalidating = …) { session -> … }` in `viewModelScope`. Roll back an optimistic change only on `Failed`; on `Obsolete` change nothing. Invalidate every `DataDomain` the write changed, the same tags main revalidates. When the response carries a resource's whole new value, pass `replacing = { listOf(store.thing.replacing(it.thing)) }` so it isn't fetched again.
- Read frame state (goals, tier, day, today, level, places, missions) from the learner summary (`learnerSummary.summary`) instead of fetching it per screen.
- Learner work that must survive process death and restarts (unsent answers, essay text, the day's choices) goes through a `DraftHandle` opened from the screen's session with `drafts.open(session, key, serializer)`: `flush()` it on `ON_STOP` and `remove()` it once the server has the work. Work that lasts only as long as the open screen (a lesson's unchecked answers, the buddy's half-written question) goes in its view model's `SavedStateHandle` instead.
- Data is kept in memory only. Don't add a disk or HTTP cache for API reads.
- Test a store only for logic it owns (races, session changes, request order, rollbacks), with JVM tests against a fake feature API (a `fun interface` the container implements with the generated client). A rule core decides belongs in core's tests, and `ResourceTest` already covers loading, staleness, dedupe, session races and invalidation.

## Sessions

- `SessionStore` is the only writer of the session and the only place credentials are stored. Don't store them anywhere else.
- Sign-in flows call `sessions.signIn(asGuest) { current -> … }` with the API call that returns the token, sending `current`'s bearer so a guest's progress moves to the account.

## Generated API client

- `:api` generates the Kotlin client on build from `api/openapi.json`, which `pnpm openapi:generate` writes from the API's contract (`pnpm openapi:check` checks it). Configure generation in `api/build.gradle.kts`; generated code is neither committed nor formatted. Fix a generator bug in a template by overriding that one template in `api/templates/`.
- Responses decode with `ApiJson` and request bodies encode with `ApiRequestJson`. A request that must send `null` for an optional field builds its body as JSON, its schema mapped to `JsonElement`.
- Stores call `api.clients(session).<tag>.<operation>()` through `perform { … }`. A request always carries the token of the session that started it; never set a token globally. Writes the server answers slowly (model grading) use `api.streamingClients(session)`.
- A screen follows a run (`202` with `generationId`) with `GenerationFollower`, as main's `useWorkflowRun` does; a read that is asked again once its content is written goes through `performWritten` and the container's `writingWaits`.

## Localization contract

- Author app-owned UI copy in English in `core/resources/src/main/res/values/`: one `strings_<feature>.xml` per feature, with every name prefixed by its feature (`today_blocks_left`) because Android merges all files into one namespace, and shared words in `strings.xml`. Use `stringResource` or `pluralStringResource`, positional placeholders, and locale-aware formatting; avoid inline UI text and concatenated sentences. Use `translatable="false"` for intentional fixed product names.
- Text the app sends or parses (an `HH:mm` time, a date, an id) never goes through the device's locale, whose digits may not be ASCII: use `java.time`'s ISO text or `Locale.ROOT`. Lint's `ImplicitLocaleFormat` reports Kotlin's `format` without a locale.
- Join a line of facts with `factsLine()`, never by hand with `" · "`.
- `@zoonk/utils/locale` owns the supported locale list; `@zoonk/i18n` owns shared translation configuration and style guides. Preserve generated Android locale configuration and system language selection rather than adding a parallel locale store or picker.
- After adding, changing, or deleting English resources, run `pnpm --filter android i18n` from the repository root. Eloqnt owns target XML and fingerprint comments, following the [translation rules](../../.agents/guides/translations.md); do not bypass freshness checks. See [localization details](README.md#localization) for targeted retranslation.
- Each `res/values/strings*.xml` is one catalog with `values-<code>/` targets; extend the catalog configuration and codec together before adding feature-module resources or qualified overrides. Retain the completeness, freshness, extra-key, placeholder/plural, unused-resource, and hardcoded Compose text checks. Suppressions need a narrow non-user-facing or preview-only reason; they must not conceal missing translations.
- `HardcodedComposeText` cannot prove that text flowing through API responses or application state is localized. Review those paths and translation quality when they change.

## Performance

- Keep composition cheap: lazy lists with `key` and `contentType`, composables below the screen taking values rather than stores, per-frame values read in lambdas (`Modifier.offset { }`, `drawBehind`). Add a package to `compose-stability.conf` only when all its types are immutable.
- LeakCanary runs in debug builds; a retained object it reports is a bug to fix.
- When a change touches data loading, stores, navigation or long-lived state, measure requests per screen and tab switch, memory, leaks, idle CPU and jank with the [verify skill's Android reference](../../.agents/skills/verify/references/android.md), and report the numbers before and after.

## Verification by impact

Follow the root completion and verification policy. The [README command reference](README.md#commands) covers setup and launch options; select checks for the affected behavior:

- For Kotlin, Gradle, or localization-tooling changes, run `pnpm android:check` from the repository root; JSON and Markdown under `apps/android` are formatted by the root `pnpm format` (oxfmt). For resource-only copy changes, run translation generation, `pnpm --filter android i18n:lint`, and the relevant native resource checks. Before committing any change beyond docs, also run Android Lint and the Release build (R8) with `make -C apps/android lint build`, which CI runs only on demand. Documentation-only edits need formatting and link checks, not a native build.
- Add a test only when it clears [the native bar](../../.agents/skills/zoonk-testing/SKILL.md#the-native-bar): JVM tests for the data layer and for races and logic the app owns, Robolectric with Compose UI test v2 (`androidx.compose.ui.test.junit4.v2`) only where the risk needs a running screen (the learner's work surviving recreation or folding), and instrumented tests (`make -C apps/android ui-test`) only for what the JVM can't run (WebView, audio, Credential Manager, Play Integrity, Auth Tab, App Links). Copy, placement and where a tap leads are checked by looking, not by tests. Call `waitForIdle()` before recreating an activity in a test.
- On a device, regexes run on Android's ICU engine, which rejects some patterns the JVM accepts (such as the `(?U)` flag), so a JVM test doesn't prove a regex works on a device.
- For UI changes, look at the result: render the affected screens on the JVM on demand ([how](../../.agents/skills/verify/references/android.md#look-at-it-without-an-emulator)) at compact, medium and expanded sizes, dark, more contrast and 200% font, then check the running app on an emulator. Renders run with `@GraphicsMode(GraphicsMode.Mode.NATIVE)`: Robolectric's legacy mode fakes font metrics, so it can't show how text lays out. A layout change also gets the `Pixel_Fold` AVD in every pose and a render with a published fold ([how](../../.agents/skills/android-material-guidelines/references/design-system.md#testing-on-a-foldable)). Don't commit golden images. Choose `en-XA`/`ar-XB` pseudolocale, TalkBack, keyboard and pointer checks based on what changed.

## Emulators and builds

Several agents may run emulators and builds on one machine. When it's overloaded, the emulator's hang detector kills the emulator, and on macOS one with a window then opens a "quit unexpectedly" alert on screen.

- Use the AVDs that exist (`emulator -list-avds`); don't create AVDs per task. Run `pnpm dev:queue` before booting one, so the boot waits while every slot is busy, then boot it headless with `-no-window -no-snapshot-save`, keep it running while you work, and shut it down when your task ends. Look at it with `adb -s <serial> exec-out screencap -p > screen.png`.
- Boot with a window only for TalkBack checks, which need its gestures; on macOS, run `pnpm dev:close-device-crash-alerts` before ending that task.
- When your emulator exits on its own, the machine was overloaded: run `pnpm dev:queue` before booting it again, so it waits for heavy jobs to make room.
- Run at most two emulators while the machine is busy. While it's quiet (the 1-minute load average in `uptime` under the core count), run up to four without asking, and shut yours down as soon as you're done. Run at most two Gradle builds at once. Never run `./gradlew --stop`: it stops every Gradle daemon of that version on the machine, including other agents' builds. Idle daemons exit on their own.
