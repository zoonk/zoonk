# Android app guidance

The [repository guidance](../../AGENTS.md) applies. This file adds Android-specific constraints; setup, commands, and implementation details live in the [README](README.md). Read the sections relevant to the task.

## Scope and architecture

- This Kotlin/Jetpack Compose app targets phones, tablets, foldables, ChromeOS, and resizable Android windows. Main defines product intent, copy, behavior, API contracts and screen structure; Apple shows how a native client reads the public API; the design system defines meaning. Build it with Android's default components, styles, and behavior. Additional platforms such as Wear OS or TV require their own product scope.
- The minimum is API 26. Don't add fallbacks below it. Above it, version checks exist only where the platform API is newer: the per-app language row (33), call audio routing (31) and the contrast level (34).
- Keep a single activity. Modules: `:app` (the shell and the features not yet in their own module), `:feature:account` (sign-in, account, settings but the licenses, statistics, subscription and feedback), `:feature:activities` (the activities and everything that draws a lesson step: step views, the lesson engine, language exercises), `:feature:catalog` (the catalog's courses, chapters and lessons, and search), `:feature:conversation` (live calls with a character, speaking practice and the speaking paper), `:feature:exam` (a goal's exam page, mock exams and essays), `:feature:onboarding` (starting a goal or a course, the goal switcher, the setup, plan links, the visitor's welcome and research notices), `:feature:plan` (the plan and its editor, goal content, mind maps, language units, the tutor and memory), `:feature:player` (the lesson player's screens, view models and reducer, explanations and pronunciation reviews), `:feature:today` (Today, the session screen, buddy and recap), `:core:resources` (every string, translation, drawable, font and asset; its namespace is `com.zoonk.android`, so `com.zoonk.android.R` is its `R`), `:core:navigation` (`AppRoute`, `AppLink`, `AppNavigator`, `AppTab`, `LearnerAccess` and `openWebPage`), `:core:data` (`AppContainer`, `data/`, every store and feature API with the models they return, and the services the container builds; its `BuildConfig` holds the API URL, client IDs and version), `:core:designsystem` (`ui/theme`, `ui/format`, `ui/components`, `ui/richtext`, `ui/characters`, the page and task scaffolds and the window's snackbar locals; it depends on no feature), `:core:ui` (learning pieces several features show and that need only core modules: listen and record controls, question views, ceremonies and day moments, missions, the Plus notice, the tab roots' scaffold, `RouteFrame`, `RoutePlaceholder`, the catalog's not-found page and the question-run kit every practice screen and essays share), `:api` (the generated client), `:lint-checks` (build time, not in the APK). `:app`'s own resources are only what it generates or must win the merge: `resources.properties` for the locale config and About Libraries' licenses, which is why the licenses screen and its route (`licensesEntries`) stay in `:app`. Every module applies a convention plugin from `build-logic` (`zoonk.android.application`, `zoonk.android.library`, `zoonk.jvm.library`), which sets the SDKs, Kotlin, Compose, lint and unit-test options once; a module's own build file keeps only what is specific to it. Packages keep their names when files move between modules, so a package can span modules. Test helpers built on a module's types live in that module's `testFixtures` (`routeSamples` in `:core:navigation`; `FakeSession`, `CountingApi` and the loopback server in `:core:data`, with the one `robolectric.properties`), which other modules' tests use with `testImplementation(testFixtures(project(…)))`.
- Where code goes: a screen, its view model and its `<Name>Navigation.kt` go in their feature module; a store, its feature API and the models it returns go in `:core:data` with the container; a piece two feature modules show that needs only core modules goes in `:core:ui`; Zoonk's theme and generic components go in `:core:designsystem`; every string and drawable goes in `:core:resources`.
- What may depend on what: core modules only on the ones before them (`:core:resources`, `:core:navigation`, `:core:data`, `:core:designsystem`, `:core:ui`); a feature module on core modules and on the feature modules it builds on, never the reverse; `:app` on everything. Gradle fails on a cycle, so a piece both directions need moves down to the lower module or to `:core:ui`.
- Adding a feature module: `feature/<name>/build.gradle.kts` applies `zoonk.android.feature` (which brings the core modules and the Compose, lifecycle, Navigation 3 and test libraries) with namespace `com.zoonk.android.feature.<name>`; include it in `settings.gradle.kts`, depend on it from `:app`, and call its entries from `AppEntries`.
- Packages: `app/` (application and shell in `:app`, container in `:core:data`), `data/`, `navigation/`, `ui/theme`, `ui/components`, `ui/format` (all three in `:core:designsystem`), `feature/<feature>/`. Device tests (`androidTest`) stay in `:app`, which runs them on the whole APK. Product code is organized by feature; a shared piece has one owning package and others call it.
- `AppContainer`, created in `ZoonkApplication`, wires everything with constructor injection: the HTTP client, `ApiClients`, `PrivateImages`, `DraftStore`, `SessionStore`, `AppCache` and every store. Don't add a DI framework. What the container builds lives in `:core:data` with it, so a store's model never sits in a screen's file; what Android creates on its own (services) reads the container through `ContainerApplication`. Debug-only behavior lives in the `debug` source set (with a no-op twin in `release` when main code calls it), never parsed in product code.
- Coroutines: the container's scope (`SupervisorJob() + Dispatchers.Main.immediate`) for caches and timers, `viewModelScope` for writes, `rememberCoroutineScope()` for UI-only work. Never `GlobalScope`. Retrofit calls are main-safe; use `Dispatchers.Default` only for measured heavy work.
- A snackbar for work that can outlive its screen goes through `AppContainer.snackbars`, never `showSnackbar` on a host captured from the window: a recreated window drops that host, so the message never shows and the work waits on it for good.
- Scope every asynchronous result and credential change to the session that started it. Before publishing or deleting state, confirm that session is still current, and test meaningful request-order races.
- Usage analytics go to PostHog from release builds only (the `posthogProjectToken` and `posthogHost` Gradle properties), as main sends them; the server records learners' outcome events from API requests. The container's `analytics` runs the SDK only while a learner (signed in or guest) is loaded and the summary's `analytics.usageDataSharing` is true, and stops it the moment the profile shows "Share usage data" turned off. It identifies the learner with main's person properties, registers main's shared properties (`platform` is `android`), and resets on sign-out or a change of learner. `ProductAnalytics.kt` sets the SDK up at the first share of each process, never at launch, with no screen views, deep links, session replay, surveys, autocapture or feature flags, and lets only event batches out, each only with the sharing learner's events, answering everything else itself, so what the SDK still holds or asks for after an opt-out or a sign-out never leaves the device. The app sends only the events main sends from the browser, typed in `AnalyticsEvent` with main's names and properties: composables through `LocalEventTracker` (`TrackShown` for a viewed or shown event, once per appearance and not again on rotation), view models through the tracker they're given. Never the SDK, and never an outcome the server already records.
- Crashes and errors go to Sentry from release builds only: `ZoonkApplication` starts it when the release build names a DSN (the `sentryDsn` Gradle property); debug builds and tests never do. Reports name no learner: no `setUser` (the SDK's random installation id stays), `sendDefaultPii`, bodies, screenshots, view hierarchy, session replay, profiling or logcat breadcrumbs. The plugin instruments only OkHttp, failed-request events are dropped (the API reports its own), `ErrorReporting.kt` strips queries and fragments from network breadcrumbs and spans, and trace headers go only to the API.
- Only `pnpm android:release` uploads the R8 mapping to Sentry, through sentry-cli's saved login (`sentry-cli login` once), so stack traces name our code. Every other release build, agents' checks included, embeds the mapping's id and uploads nothing, even on a machine signed in to sentry-cli.

## Native UI

- For UI, navigation, or interaction work, use [Zoonk design](../../.agents/skills/zoonk-design/SKILL.md) for the experience and what things mean, the [Android Material guidelines skill](../../.agents/skills/android-material-guidelines/SKILL.md) for components, styles, and behavior, and current official documentation relevant to the change. Use what Material 3 and Android provide by default (`MaterialTheme` color, type, and shape roles, the `sp` type scale, Material Symbols, AndroidX components, adaptive scaffolds) and express the design system's meaning through them, with Zoonk's color scheme rather than dynamic color. No raw colors, fixed font sizes, or fixed frames in composables; add custom styles or assets only where no platform equivalent carries the meaning (characters, belts), and make them adapt to dark theme, contrast, and font scale.
- Navigation 3 with typed routes: `navigation/AppRoute.kt` declares every main path with its presentation (tab, page, section, task, web page) and requirement (none, account, goal), and `navigation/AppLink.kt` reads main's URLs into them. A feature registers its routes' screens, with their scene metadata, only in its own `feature/<name>/<Name>Navigation.kt`; a route without its screen shows `RoutePlaceholder`. Features navigate only through `AppNavigator`, which keeps one back stack per tab.
- Web pages open only through `openWebPage`, which shows a Toast when nothing on the device can open them, since a Custom Tab with no browser throws; a Toast, unlike a snackbar, also shows over sheets and dialogs.
- The shell is Material's navigation suite: a bar on compact windows, a rail on medium ones, and a drawer that also lists the Study places on expanded ones. Tasks cover it. Build tab roots on `TabRootScaffold`, pages on `PageScaffold`, tasks on `TaskScaffold` and pages with an aside on `PageWithSupportingPane`. `TabRootScaffold` (in `:core:ui`) shows the app bar `ZoonkApp` provides through `LocalTabRootBar`, since the goal switcher, level, account menu and search belong to features above the tabs; a test that shows a tab root outside the shell wraps it in `WithTabRootBar`.
- Adapt to the current window size and available space with window size classes and measured space, never device checks. Preserve state across resizing, folding, rotation, and recreation; keep orientation and resizing unrestricted. Use canonical multi-pane layouts when content benefits from them.
- Preserve edge-to-edge and accessible system bars, consume scaffold padding once, and account for cutouts and the keyboard. Retain Android back behavior, 48dp touch targets, font scaling, TalkBack semantics, RTL, and keyboard/pointer access as relevant controls change.
- When using a Material Symbol, first check what symbol is used for this feature in the `apple` and `main` apps. Then, choose the closest Material Symbol. Symbols/icons should be consistent across platforms.
- Everyday screens are still. Celebrations are rare and earned, follow [Zoonk motion](../../.agents/skills/zoonk-motion/SKILL.md), and stay still when the animator duration scale is 0.
- Private pictures (the API's `/v1/files/`) load through `images.request(context, url, session)` with the session the screen shows: the bearer goes in that request's own headers, the session's `localId` in its memory key, and nothing on disk. Never add the bearer through an interceptor that reads the current token.
- Sound goes through the container's `speech` player (`feature/audio`), one sound at a time for the whole app: listen buttons use `rememberSpokenAudio` and `ListenButton`, and a clip is requested only from the tap. Recorded answers use `VoiceAnswerRecorder`, which asks for the microphone on the first Record tap and grades through the screen's write; a screen whose own state grades each take (pronunciation reviews) holds a `VoiceRecorder` in its ViewModel with `rememberRecordTap` and `RecordButton`. Never create another `ExoPlayer` or `MediaRecorder`.
- Learner code (JavaScript, Python, SQL, regexes) runs only through the container's `codeSandbox`, one hidden WebView hosting main's player sandbox; never another WebView, JavaScript engine or `java.util.regex` for it. Its page, `assets/sandbox/index.html`, is generated: run `pnpm --filter android sandbox` after main's sandbox changes.

## Data loading and caching

Every read the app shows goes through one pattern in `data/`, so screens are instant on return:

- Stores create their reads with `cache.resource(audience, domains, maxAge, isEmpty) { session -> … }` and own the returned `Resource<T>`. Stores live in the container for the app's lifetime, so data survives tab switches, back navigation and recreation. Only stores create resources.
- Each API read has one owning store, and every screen that shows it derives from that store's resource rather than a second read or a copy. A read several screens share gets a counting test (`CountingApi`, the real Live client against a loopback server) so a screen that adds a request fails.
- A `Resource` loads once, shows `Loading` only when nothing is cached, revalidates in the background when older than `maxAge` (5 minutes by default) or invalidated, shares one request among concurrent callers, keeps content when a refresh fails (except `NotFound`, which an invalidation drops), signs out on `Unauthorized`, and drops a response whose session ended. `Audience` decides what a session change does: `Everyone` (kept), `Viewer` (public but personalized, dropped) or `SignedIn` (the learner's own, idle while signed out, dropped). A dropped resource a screen still shows loads the new session's value at once.
- A screen shows a resource with `val state by store.thing.collectShown()` and switches on `LoadState` (`Idle`, `Loading`, `Loaded`, `Empty`, `Failed`). Only that collection counts as viewing: it loads on appear and when the app returns to the foreground. Pull to refresh and retry call `refresh()`. Never start requests in `LaunchedEffect(Unit)` or `init {}`, never copy a resource's value into another state holder, and always pass the store's instance.
- Small frame and tab reads are plain resources. Heavy reads by id (course, chapter, lesson, tutor thread, mock result) use `cache.keyed(…)`, which keeps every key a screen shows plus the 8 most recent and releases the rest on memory pressure; never keep resources in an unbounded map. Pagination appends with `resource.update` after checking `resource.revision` didn't change while the page loaded. A task that opens over a screen calls that store's `prepare()` so the screen is ready when uncovered.
- A screen gets a ViewModel, scoped to its navigation entry, only when it writes or holds in-progress work. It exposes store resources as they are.
- Run every write through `cache.mutate(invalidating = …) { session -> … }` in `viewModelScope`. It sends that session's token, signs that session out on `Unauthorized`, and returns `Done`, `Failed` or `Obsolete` (the session ended or changed meanwhile). Roll back an optimistic change only on `Failed`; on `Obsolete` change nothing. Invalidate every `DataDomain` the write changed, the same tags main revalidates in `packages/core/src/cache/tags.ts`. When the response carries a resource's whole new value, pass `replacing = { listOf(store.thing.replacing(it.thing)) }`: the value shows as fresh, an older read can't overwrite it, and that resource isn't fetched again.
- The learner summary (`learnerSummary.summary`, `getCurrentUserSummary`) is one `SignedIn` resource reading every domain, collected by the frame and marked stale at its `nextChangeAt`. Read frame state (goals, tier, day, today, level, places, missions) from it instead of fetching it per screen.
- Learner work that must survive process death and restarts (unsent answers, essay text, the day's choices) goes through a `DraftHandle` opened from the screen's session: `drafts.open(session, key, serializer)`. It reads and writes only that account's file, even after another learner signs in; `saveDebounced` saves end with the session. Call `flush()` on `ON_STOP` and `remove()` once the server has the work. Only the signed-in account's file exists on the device: `SessionStore` deletes it on sign-out or an account switch and merges a guest's into the account it upgrades to.
- Data is kept in memory only. Don't add a disk or HTTP cache for API reads.
- Cover a new store's own logic with JVM tests against a fake feature API (a `fun interface` the container implements with the generated client); `ResourceTest` already covers loading, staleness, dedupe, session races and invalidation.

## Sessions

- `SessionStore` is the only writer of the session. It shows or stores a token only after `getCurrentUser` accepts it, restores the stored one at launch, and on each change lets the cache, drafts and private pictures follow before anything else runs.
- Sign-in flows call `sessions.signIn(asGuest) { current -> … }` with the API call that returns the token, sending `current`'s bearer so a guest's progress moves to the account. A result of `Obsolete` means another sign-in finished first. Sign out with `signOut()`; after an account is deleted, call `forgetDeletedAccount(session)`. `learnerAccess` in the container turns the session and the summary into what the shell's gates read.
- The token is in DataStore encrypted with Tink under an Android Keystore key, excluded from backup. Don't store credentials anywhere else.

## Generated API client

- `:api` generates the Kotlin client on build from `api/openapi.json`, which `pnpm openapi:generate` writes from the API's contract (`pnpm openapi:check` checks it). Configure generation in `api/build.gradle.kts`; generated code is neither committed nor formatted. A union the generator can't express becomes `JsonElement` through `schemaMappings`; a generator bug in a template is fixed by overriding that one template in `api/templates/`.
- Integers decode as `Long` (some are epoch milliseconds) and numbers as `Double`. Responses decode with `ApiJson`, which keeps the generated contextual serializers. Request bodies encode with `ApiRequestJson`: a field the contract requires keeps its `null`, and an optional field left unset stays out, so a PATCH sends only the fields it sets. Only an optional field whose `null` means something other than absent (`LearningProfileUpdate`, a course start's `level`) needs its body built with `buildJsonObject`, its schema mapped to `JsonElement`.
- Stores call `api.clients(session).<tag>.<operation>()` through `perform { … }`, which returns the body or throws `ApiException` with an `ApiError` (`Network`, `NotFound`, `Unauthorized`, `Unavailable`) and the API's error `code`, and lets cancellation through. A request always carries the token of the session that started it; never set a token globally. Writes the server answers slowly (model grading) use `api.streamingClients(session)`.
- Generation progress streams through `api.generationEvents(id, session)`, which resumes a dropped connection from the last event received.

## Localization contract

- Author app-owned UI copy in `core/resources/src/main/res/values/`, the complete English fallback: one `strings_<feature>.xml` per feature, with every name prefixed by its feature (`today_blocks_left`) because Android merges all files into one namespace, and shared words in `strings.xml`. Use `stringResource` or `pluralStringResource`, positional placeholders, and locale-aware formatting; avoid inline UI text and concatenated sentences. Use `translatable="false"` for intentional fixed product names.
- Join a line of facts with `factsLine()`, never by hand with `" · "`: it puts a no-break space before each `·`, so a wrapped line never starts with one.
- `@zoonk/utils/locale` owns the supported locale list; `@zoonk/i18n` owns shared translation configuration and style guides. Preserve generated Android locale configuration and system language selection rather than adding a parallel locale store or picker.
- After adding, changing, or deleting English resources, run `pnpm --filter android i18n` from the repository root. It refreshes missing/stale translations, prunes removed entries, and finishes with strict validation. Eloqnt owns target XML and fingerprint comments, following the [translation rules](../../.agents/guides/translations.md); do not bypass freshness checks. See [localization details](README.md#localization) for the codec and targeted retranslation workflow.
- Keep translatable resources within the configured catalogs: each `res/values/strings*.xml` is one catalog with `values-<code>/` targets. Extend the catalog configuration and codec together before adding feature-module resources or qualified overrides. Retain completeness, freshness, extra-key, placeholder/plural, unused-resource, and hardcoded Compose text checks. Suppressions need a narrow non-user-facing or preview-only reason; they must not conceal missing translations.
- `HardcodedComposeText` cannot prove that arbitrary text flowing through API responses or application state is localized. Review those paths and translation quality when they change.

## Performance

- Screens feel instant: show cached data at once and revalidate in the background; show a loading state only when nothing is cached. Load each fact once and never refetch on recomposition, resume or tab switch.
- Keep composition cheap: lazy lists with `key` and `contentType`, composables below the screen taking values rather than stores, per-frame values read in lambdas (`Modifier.offset { }`, `drawBehind`). The generated models are declared stable in `compose-stability.conf`; add a package there only when all its types are immutable.
- LeakCanary runs in debug builds; a retained object it reports is a bug to fix.
- When a change touches data loading, stores, navigation or long-lived state, measure requests per screen and tab switch, memory, leaks, idle CPU and jank with the [verify skill's Android reference](../../.agents/skills/verify/references/android.md), and report the numbers before and after.

## Verification by impact

Follow the root completion and verification policy. The [README command reference](README.md#commands) covers setup and launch options; select checks for the affected behavior:

- For Kotlin, Gradle, or localization-tooling changes, run `pnpm android:check` from the repository root. It covers translation validation, tooling/JVM tests, Kotlin and Gradle formatting, and the JVM unit tests; JSON and Markdown under `apps/android` are formatted by the root `pnpm format` (oxfmt), which CI checks too. For resource-only copy changes, run translation generation, `pnpm --filter android i18n:lint`, and the relevant native resource checks. Before committing any change beyond docs, also run Android Lint and the Release build (R8) with `make -C apps/android lint build`: CI runs them only on demand because they take over 5 minutes there. Documentation-only edits need formatting and link checks, not a native build.
- Test behavior, not composables: JVM tests for stores and non-trivial logic; Robolectric with Compose UI test v2 (`androidx.compose.ui.test.junit4.v2`) for user flows and window sizes (`@Config(qualifiers = …)`, font scale, night); instrumented tests (`make -C apps/android ui-test`) only for what the JVM can't run (WebView, audio, Credential Manager, Play Integrity, Auth Tab, App Links). Call `waitForIdle()` before recreating an activity in a test.
- A test that measures text (wrapping, line counts, overflow) runs with `@GraphicsMode(GraphicsMode.Mode.NATIVE)`: Robolectric's legacy mode fakes font metrics, so it can't show how text lays out.
- On a device, the app's regexes run on Android's ICU engine, which rejects some patterns the JVM accepts (such as the `(?U)` flag), so JVM tests don't prove a regex works on a device; `RichTextOnDeviceTest` renders lesson text there.
- For UI changes, look at the result: render the affected screens on the JVM at compact, medium and expanded sizes, dark, more contrast and 200% font, then check the running app on an emulator. Don't commit golden images. Choose `en-XA`/`ar-XB` pseudolocale, TalkBack, keyboard and pointer checks based on what changed. A build or a JVM render does not establish runtime behavior; report what was actually observed and any unverified coverage.

## Emulators and builds

Several agents may run emulators and builds on one machine. When it's overloaded, the emulator's hang detector kills the emulator, and on macOS one with a window then opens a "quit unexpectedly" alert on screen.

- Use the AVDs that exist (`emulator -list-avds`); don't create AVDs per task. Run `pnpm dev:queue` before booting one, so the boot waits while every slot is busy, then boot it headless with `-no-window -no-snapshot-save`, keep it running while you work, and shut it down when your task ends. A headless emulator opens no window, and its crash opens no alert. Look at it with `adb -s <serial> exec-out screencap -p > screen.png`.
- Boot with a window only for TalkBack checks, which need its gestures; on macOS, run `pnpm dev:close-device-crash-alerts` before ending that task.
- When your emulator exits on its own, the machine was overloaded: run `pnpm dev:queue` before booting it again, so it waits for heavy jobs to make room.
- Run at most two emulators and two Gradle builds at once. Never run `./gradlew --stop`: it stops every Gradle daemon of that version on the machine, including other agents' builds. Idle daemons exit on their own.
