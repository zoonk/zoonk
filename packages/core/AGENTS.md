# Core capabilities

- `@zoonk/core` is the shared Next.js-aware server and business package for Main, API, Admin, and the clients that reach those capabilities through the API.

## Capability boundaries

- If an app must coordinate multiple core calls to perform one coherent API-like operation, add a resource- or domain-capability leaf in core instead of duplicating that orchestration across apps. Do not create page-sized aggregate functions or expose one function per Prisma query.
- Public authenticated core functions call the shared `getSession()` capability themselves and own every permission check. Apps may pass untrusted resource IDs and validated input, but they must never pass a caller-selected acting `userId` to a public core capability.
- Internal core helpers may receive a user ID only after a public core boundary derives it from the authenticated session. Do not export those helpers as authorization boundaries. On GET paths, load each request-stable fact through its one canonical private leaf in `learner/facts/`, behind the public capability's authorization. Helpers receive already-loaded facts instead of IDs to re-read. Write and workflow preconditions keep fresh reads.
- Import core capabilities through direct package subpath leaf exports. Do not create a monolithic facade or root barrel that imports every feature; client-only, workflow-safe, and server-only leaves must remain separate so unused dependencies stay outside each consumer's module graph.

## Reads, caching, and invalidation

- Use `"use cache"` for reusable caller-independent reads and `"use cache: private"` for authenticated or request-dependent reads that need request deduplication and runtime prefetching. Dedupe is exact on the function and Flight-serialized arguments, across nested scopes, concurrent calls and Route Handlers. Use stable primitive arguments; varying clock values and different object shapes create different keys. `React.cache` does not share results across cache scopes or memoize Route Handler calls. Cache the complete exported read capability when instant navigation depends on its full result.
- Load each fact once per request: the plan, the goal, the subscription or the day's totals that several GET reads of a page need come from one leaf with the union of the columns they use, tagged with what its writers expire (`readSavedPlan`, `readDayProgress`); a `select` per helper is the same fact read again. Every call of a cached read, joined ones included, decodes its whole result, so a large fact costs once per reader: leave out columns no reader uses, and keep a cached result to what its callers read. A helper shared with writes takes the loaded fact as an optional argument that GET callers pass. Store a derived fact on write only when computing it on read, not reading its inputs, is what costs.
- A `"use cache: private"` read is never kept on the server in production, but the browser reuses it (prefetched or visited) for its stale time. `next dev` keeps it in memory and answers the next matching request with it while reading again, so a private read carries the tags its learner rows' writers expire, or the first read after a write shows the old result in development. A Server Action that expires tags clears every copy the browser holds and re-renders the page it ran on. Flows that keep state on screen across writes (a session's moments, answers through main's app routes) don't expire tags from the action. Main notes its posts to app routes and the API on its own; a Server Action that doesn't expire tags is wrapped in `noteAppWrite` where it's called; `RefreshStalePages` then reads the stale pages again. Freshness has no other layer: no revision counters, no "did anything change" checks.
- `"use cache: private"` goes on the read function nearest the request, never on a component or a page: everything in one scope shares its lifetime, so a component in it caches its markup with the learner's data. Shared content a private read needs (courses, chapters, skills, Library lessons) comes from the shared `"use cache"` leaves it calls, keyed as the cross-app rule below says; the private scope covers the learner's own rows.
- Do not blanket-cache every Prisma read. Mutations, authorization preconditions whose freshness controls a write, generation polling, and durable workflow-step reads remain uncached unless their freshness and invalidation contract is explicitly designed.
- Do not convert session or persistence failures into `null` inside reusable core reads or Cache Component leaves. Reserve `null` for legitimate missing data, let infrastructure failures propagate for HTTP 5xx mapping, and place any intentional web-only graceful fallback in the owning app outside the `"use cache"` or `"use cache: private"` leaf.
- Don't call `cacheLife`: every cache uses Next's default profile (5 minutes in the browser, enough for a private read to ride in a route's App Shell; revalidated after 15 minutes on the server). Another lifetime needs a correctness requirement or a feature the installed Next docs tie to one.
- Reads that a page renders never read the clock or randomness (`new Date()`, `Date.now()`, `Math.random()`, `randomUUID()`) where a prerender can reach it: Next.js reports "encountered the unstable value" on that route. GET paths share one request instant (`getRequestInstant` in `learner/facts/request-instant.ts`), so a prefetched read keeps the instant it was read until the browser reads it again. Derive each goal's local day from that goal's stored zone, never UTC or the server's. A read that must be fresh on every request and isn't prefetched calls `await io()` from `next/cache` right before the clock. Never `connection()` in core: it blocks prefetches. Time shown only for display ("3 minutes ago") is computed in the browser.
- Normalize route values and other semantically equivalent inputs before calling a regular `"use cache"` leaf so encoded and decoded values share one canonical cache key.
- Core mutations own cache-tag invalidation and return only their domain resource or outcome. Use `revalidateCacheTags(tags)` (`src/cache/revalidate-cache-tags.ts`), never `revalidateTag` directly. Each Next.js app has its own cache: a course-content write calls `revalidateCourseContent(tags)` after committing, which also expires Main's copies when the API wrote, and an API workflow step wraps that write in `collectCourseContentTags` so its workflow delivers the tags (`deliverCourseContent`) and a failed delivery retries without repeating the write. Other cross-app shared reads use a cheap fresh version key (as `getPlayableLibraryLesson` does), or the default revalidation where a short delay is harmless. Apps retain only route-specific `revalidatePath()` calls.

## Admission

- Work that costs (a model call, a download or parse, paid research) is admitted by a claim before it starts, inside the capability that does the work, so a new caller (another route, a correction, a guest, a background check) can't reach the work without it. A claim is a row under a unique key, or a count and an insert under the learner's lock in one short write ([`claimUsage`](src/entitlements/claim-usage.ts) and its siblings), never a transaction held open across the work. A cap counts its claims, not what the work saves afterward. A claim keyed by the request charges a retry once, but `claimUsage` still answers it as allowed: to run the work once, only the request whose insert won does it, and the others replay its saved result or follow its run.
- What decides a charge, a share, a replacement or "already done" lives in a column only core writes, never in a field clients send or edit (`details`, a reported length or count).

## Follow-ups and generation

- A write calls `oweFollowUps` in the branch that actually changes the row (the first time a session ends, not a repeat call that finds it ended), never returning a "start this next" result for apps. A workflow that makes the write starts its next run itself, from the step's result.
- Shared content has no learner to owe work to, so the work its write owes (a picture's check, an exam's freshness check) is a column on its row that the write sets and the work clears, such as `MediaAsset.checkOwedAt`. The daily sweep starts what's still owed, and every run doing that work holds the row's run token and claims an attempt first, so it never runs twice at once or keeps paying for a failure no retry fixes.
- A capability that needs content nobody has written returns what to write and its key instead of writing it, before it starts, charges or reserves anything, since the client sends the same request again once that content is written. The API turns that into a run.

## Learner data

- Progress and stats reads never join content tables. They read learner-owned rows, such as daily totals and activity records, so every number survives content being deleted, merged, or regenerated.
- Learner rows never cascade from content. Reference content with `onDelete: SetNull`, or keep a plain id with a snapshot of what the learner saw, such as the title.

For Prisma query shapes, use the shared [Prisma guidance](../../.agents/guides/prisma.md). React leaves in this package also follow the shared [web guidance](../../.agents/guides/web.md).
